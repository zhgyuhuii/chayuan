# 加载项内置检查 vs Claude Code MCP：两条审查路径怎么选

察元装进 WPS 之后，至少有两条路能对当前文档做自动审查。一条是加载项里的「拼写与语法检查」（以及助手页相关能力），人坐在 WPS 前点选。另一条是 Claude Code（或其他 MCP 客户端）连接本机服务 `chayuan-wps-mcp`（`http://127.0.0.1:62588/mcp`），用自然语言编排打开文档、分块、预览、确认写批注。两条路不是对立产品，而是同一套本机能力上的不同操作面。本文按场景对比，避免「必须上 Claude」或「有按钮就够了」两种极端。

健康检查：`http://127.0.0.1:62588/healthz`。官网 [aidooo.com](https://aidooo.com)，发行页 [GitHub Releases](https://github.com/zhgyuhuii/chayuan-wps-releases)，Claude MCP 通识 [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp)。接通验收见 [healthz 与四级验证](./09-healthz-four-level-verify.md)。

![两条审查路径对照示意](images/csdn-10-1.png)

## 先说共同点

1. 都作用在本机 WPS 文档上，不是把稿件上传到无关网页再下载回来（模型供应商是否云端，取决于你在察元里怎么配）。
2. 写批注、替换一类写回应当可控；MCP 路径对批注与替换有明确确认门闩，加载项界面也提供预览与写回出口。
3. 校对质量依赖你在察元设置里配置的模型。没配模型时，两条路都会在校对环节失败或报 `MODEL_NOT_CONFIGURED`。
4. 表格锚点、长文分块等底层能力在产品侧是同一套方向；MCP 只是把能力暴露成工具。

因此排错顺序永远是：WPS 与加载项 → healthz → 模型 → 再谈 Claude 配置。不要反过来。

## 路径 A：加载项内置拼写与语法检查

### 适合谁

1. 主要工作面就在 WPS，不需要终端。
2. 单文件、中短篇，当场出问题列表或批注。
3. 培训成本要低：会点功能区即可。
4. 用于验证「本机审查链路是否健康」，作为装机冒烟。

### 典型步骤

1. 打开文档，故意留两三个错字做测试。
2. 在察元 AI 助手或文本分析入口执行拼写与语法检查。
3. 看问题列表；需要时写成批注。
4. 抽查正文与表格高亮是否钉在错字上。

### 强项

操作路径短；进度与结果都在办公界面里；对不写代码的岗位友好。大文档上产品侧也有分块与进度优化，不一定非开 Claude。

### 边界

跨多份文件自动切换、和仓库/脚本/其他 MCP 工具编排、在终端里把「审 WPS」嵌进更大任务，不是这条路径的主场。复杂开场白与多步分支，用对话智能体更顺，但也仍在 WPS 窗格里完成。

![加载项拼写检查问题列表](images/csdn-10-2.png)

## 路径 B：Claude Code + chayuan-wps-mcp

### 适合谁

1. 已在用 Claude Code 做开发或文档自动化。
2. 需要多文档交叉、按路径打开、与 git/脚本同会话。
3. 需要严格的「先预览，再说确认写批注」话术固化在开场白。
4. 要把审查步骤写进可重复的指令包。

### 典型步骤

1. healthz online；`claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62588/mcp`。
2. 四级验收通过（列表、工具、只读、预览）。
3. 粘贴开场白，只要求预览。
4. 人工确认后回复「确认写批注」。
5. 需要时再「确认替换」；表格强调钉在单元格错字上。

### 强项

编排能力：`document_open`、`document_meta`、`document_chunks`、`document_locate`、批量 ops 预览等可以按你的句子组合。多文档交叉见 [多文档交叉校对](./08-multi-document-cross-proofread.md)，长文见 [长文档分块审查](./07-long-doc-chunk-review.md)，表格见 [表格批注锚点](./06-table-comment-anchor.md)。

### 边界

前置条件更多：Claude 登录与权限、MCP 配置、WPS 保持打开。客户端上下文窗口与模型习惯会影响「是否擅自全文 get_text」。必须用开场白把禁止项写死。未确认写回时出现 `CONFIRMATION_REQUIRED` 是设计。

![Claude 预览列表与 WPS 批注同屏](images/csdn-10-3.png)

## 对照表

| 维度 | 加载项内置检查 | Claude Code MCP |
| --- | --- | --- |
| 主界面 | WPS | 终端 / Claude |
| 单文件错别字 | 强，路径短 | 强，需配置 |
| 多文档调度 | 弱（人手切换） | 强（document_open） |
| 长文策略 | 产品内分块进度 | meta + chunks 剧本 |
| 与其他工具编排 | 有限 | 强 |
| 培训成本 | 低 | 中 |
| 确认写批注 | 界面操作 | 对话确认 |
| 依赖 healthz | 间接（本机服务） | 直接 |
| 典型失败 | 模型未配 | 离线码 / 配置错 / 模型未配 |

## 怎么选型（决策树）

1. 只会 WPS、只要错别字 → 加载项。
2. 要交叉多份招标/合同附件 → Claude MCP。
3. 装机验收 → 先加载项自检，再四级 MCP 验收。
4. 内网无 Claude → 加载项 + 内网模型；或换其他 MCP 客户端接同一 `chayuan-wps-mcp`。
5. 已有 OpenClaw / Codex / Hermes → 与 Claude 相同，走 MCP，不必绑死一家客户端。

助手页若开启「文档智能体」，也可能走同一本机 MCP，与外部客户端共用 sidecar。此时更要避免同一文档上两个客户端同时疯狂写回；写回串行、先预览后确认。

## 共用 sidecar 时的协作规矩

1. 本机只跑一份监听 `127.0.0.1:62588` 的服务。
2. 多个客户端可以同时连，但写批注与替换按文件加锁式处理：一个人确认写回时，另一个人不要并行确认替换。
3. `WPS_AGENT_OFFLINE` 时所有客户端一起失败，回 WPS 与加载项，不是只重装 Claude。
4. 升级察元后，加载项与 MCP 工具表可能变化，两端都做一次冒烟。

## 同一份测试稿的双路径验收

造一份含正文错字与表内错字的短稿。

### 加载项

跑拼写与语法检查 → 写成批注 → 看表内是否挂整格。

### Claude

只读文件名 → 校对预览 → 确认写批注 → 再看批注窗格。

若加载项钉得准、Claude 挂整格，优先改 Claude 指令（钉在具体错字上），不是重装。若两边都挂整格，按表格篇排查版本与原文粒度。若加载项能出列表、Claude 第四级报模型未配，检查是否走了不同的校对入口或设置未保存。

![双路径同一测试稿验收](images/csdn-10-4.png)

## 提示词与界面操作的对应关系

| 你在 Claude 说 | 近似于加载项 |
| --- | --- |
| 校对预览，不要写批注 | 先跑检查看列表 |
| 确认写批注 | 把问题写成批注 |
| 确认替换 | 接受修改写回正文 |
| 打开路径 X | 在 WPS 里打开文件 |
| 用 chunks 阅读 | 长文分段处理（产品内建） |

把这张表发给科室，有助于两边同事沟通，而不要用两套黑话。确认策略细节见 [确认策略与安全边界](./14-confirm-strategy-safety.md)；开场白见 [提示词与开场白](./05-prompt-and-opening.md)。

## 安全与合规层面的相同要求

1. 涉密与定稿以人工和单位制度为准。
2. 云端模型会把片段发到供应商时，按单位规定选型；可改内网兼容端点。
3. 默认 MCP 只绑本机回环地址，不把 62588 裸暴露到公网。
4. 批量替换前保留副本；批注是可审计痕迹，替换是直接改历史。

两条路径都不会自动替你承担签发责任。差异只在操作面上：按钮还是对话。

## 何时应该从加载项升级到 Claude

出现以下信号再投入 MCP 培训：

1. 每周多次多文档口径核对。
2. 已有人用 Claude Code 处理同类事务。
3. 需要把审查步骤固化成可粘贴指令包，而不是口头教点哪里。
4. 要和仓库、脚本、其他 MCP 工具同会话。

没有这些信号时，加载项足够，强推 Claude 只会增加装机失败面。反过来，已经在 Claude 里工作的人，不必为了审 WPS 再学一套完全不同的产品逻辑——挂上 `chayuan-wps-mcp` 即可。

## 实施建议（一周）

1. 第 1 天：全员加载项安装，healthz online，加载项自检通过。
2. 第 2 天：配置模型，短稿批注抽查。
3. 第 3 天：给需要的人装 Claude MCP，跑四级验证。
4. 第 4 天：表格锚点专项。
5. 第 5 天：长文 chunks 或多文档交叉选一个场景练兵。

这样铺开，成本可控，也避免第一天就上交叉校对。总览仍可回看 [全生命周期安装与审查](./01-lifecycle-install-to-claude.md)。

## 成本与账号因素

加载项路径的成本主要在模型供应商与察元授权；人不需要额外 Claude 账号。Claude 路径叠加 Anthropic 侧账号、权限与计费规则，还要满足单位是否允许终端智能体访问办公稿件。选型时把「账号能不能发到该岗位」写进决策，而不是只比较功能清单。

内网单位常见结论：全员走加载项 + 内网模型；少数文档自动化岗位再开 MCP 客户端（Claude 或其他）。同一 `chayuan-wps-mcp` 也可被 Codex、Cursor、Hermes、OpenClaw 使用，不必为了 WPS 绑定单一聊天壳。

## 界面文案与话术对齐

加载项按钮可能写「拼写与语法检查」「写成批注」「直接改正正文」。Claude 侧对应「校对预览」「确认写批注」「确认替换」。培训材料应给出对照，避免甲说「我点了检查」、乙说「我 dryRun 了」却以为彼此在做不同事。

建议在科室维基置顶五句标准话：

1. 先预览，再确认写批注。
2. 没有确认替换，不改正文。
3. 表格钉在错字上，不挂整格。
4. 多文档写回前先报文件名。
5. 连不上先看 healthz。

五句对两条路径都成立。

## 故障责任怎么划分

| 现象 | 先查加载项 | 先查 Claude |
| --- | --- | --- |
| 功能区没有察元 | 是 | 否 |
| healthz 非 online | 是（本机服务） | 否 |
| 加载项能查、Claude 列表无服务 | 否 | 是 |
| 两边都报模型未配 | 是（设置） | 否 |
| 仅 Claude 报离线 | 看 WPS 是否被关 | 是 |
| 仅 Claude 挂整格 | 对照加载项锚点 | 改指令 |
| 两边都挂整格 | 产品/版本/原文粒度 | 同左 |

责任表能减少「两个入口互相踢皮球」。错误码细节见排错篇。

## 混合工作流示例（真实一天）

上午：业务同事在 WPS 用加载项清完请示正文错别字，并确认写批注。  
下午：文档自动化同事用 Claude open 请示、说明、附件清单，出交叉表，按文件追加交叉类批注。  
傍晚：业务同事只在 WPS 批注窗格处理「严重」项，决定是否确认替换。

此混合不要求全员学终端，又能把交叉核对做掉。关键是下午写回前不要清掉上午的批注，除非明确要重跑。

## 何时不应使用自动审查

1. 尚未另存副本的唯一定稿。
2. 制度明确禁止该模型供应商出域的文稿（又未配内网模型）。
3. 需要法律或保密资质签署的材料，自动审查最多做辅助列表。
4. healthz 或四级验收未通过的机器。

两条路径都遵守同一张「不应使用」清单。路径差异不构成合规豁免。

## 指标：怎么知道选型选对了

试行两周后看三个数：

1. 单文件错别字平均耗时（加载项应明显短）。
2. 多文档交叉任务是否还在用人工左右开窗（若是，MCP 培训没到位或根本不该逼全员上 Claude）。
3. 串稿与挂整格事故次数（应为零；出现一次就复盘指令与确认话术）。

用事故次数而不是「模型回复是否流畅」当指标。流畅但写错文件，是负分。

## 相关配置与排错

模型供应商细节见模型配置篇；确认门闩见确认策略篇；错误码见排错篇；公文合同场景见场景篇。本篇只解决「早上打开 WPS 还是打开终端」这一层。读完应能写下本科室的默认路径：全员加载项，或全员加载项 + 岗位 MCP，而不是「听说 Claude 更强所以全员切换」。

## 小结

加载项内置检查是办公界面上的短路径；Claude Code MCP 是编排与多文档的长路径。它们共用本机 sidecar、同一活动文档和同一套确认写回思想。选型看工作面与是否需要调度，不看哪边「更 AI」。先让加载项与 healthz 绿，再让 Claude 过四级，最后才把表格、长文、多文档的专项指令加进去——这是稳妥顺序。把五句标准话和责任表发到科室，两条路径才能一起用，而不是互相打架。若只能记住一句话：不会终端就用加载项；要跨文件编排再上 MCP，且上之前必须四级验收通过。
