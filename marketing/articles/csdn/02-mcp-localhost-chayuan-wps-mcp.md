# 本机 MCP：端口 62588、chayuan-wps-mcp 与 Streamable HTTP

察元 AI 文档助手 v4.0 把「智能体如何碰到本机 docx」收成一件事：本机 sidecar 提供 Streamable HTTP 形态的 MCP，固定监听 `127.0.0.1:62588`。客户端不负责启动 WPS，也不负责装 Node；它只要连对 URL、选对传输方式、别乱填 Token。本文只讲这一层：协议形态、端口与路径、自启行为、无 Token 边界，以及连不上时怎么分层拆。

![本机sidecar监听62588结构示意](images/csdn-02-1.png)

## 服务名、URL 与健康检查

服务名建议在所有客户端里统一写成 chayuan-wps-mcp。少写后缀、自创别名，会在多人协作时变成「每人一个名字」，排错时对不上。

MCP 入口：

```
http://127.0.0.1:62588/mcp
```

健康检查：

```
http://127.0.0.1:62588/healthz
```

浏览器打开 healthz，期望看到在线或 online。healthz 只回答服务是否起来，不代替「工具列表是否完整」或「校对模型是否已配」。MCP 路径给支持 Streamable HTTP 的客户端握手与调工具。两条路径不要混用：把 healthz 填进 MCP 配置，或把 mcp 当网页刷新看状态，都会得到令人困惑的结果。

官方 MCP 说明见：[Claude Code MCP 文档](https://code.claude.com/docs/en/mcp)。安装总览见：[全生命周期安装与审查](./01-lifecycle-claude-wps-review.md)。发布包与版本说明入口：[GitHub Releases](https://github.com/zhgyuhuii/chayuan-wps-releases)、[官网](https://aidooo.com)。

![浏览器打开healthz返回online](images/csdn-02-2.png)

## Streamable HTTP：不要配成 stdio

Claude Code 注册命令：

```
claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62588/mcp
```

transport 用 http；部分界面写作 Streamable HTTP，按同义处理。不要配成 stdio 去启动某条本地命令。v4.0 安装包已内嵌 sidecar 并注册开机自启，客户端侧只做「连接」，不做「拉起进程」。

`.mcp.json` 示例：

```json
{
  "mcpServers": {
    "chayuan-wps-mcp": { "url": "http://127.0.0.1:62588/mcp" }
  }
}
```

Codex 一类客户端用 toml 段填写同一个 url。图形客户端新建 MCP 时：类型选 HTTP 或 Streamable HTTP，URL 填本机地址，名称填 chayuan-wps-mcp。

![Claude Code MCP列表出现chayuan-wps-mcp](images/csdn-02-3.png)

### 无 Token 是设计不是疏忽

当前本机服务按设计不走 Token。有人为了「更安全」随手填一个假 Token，反而导致握手失败。信任边界是本机登录会话：同一台机器上的其他进程理论上可以连 62588，但这和「已经暴露到公网」不是一回事。不要把 62588 做端口映射到互联网。远程要用，自行加隧道或反向代理，并按单位规范评估。

## sidecar 自启与和 WPS 的关系

安装后 sidecar 一般随用户登录自启。但「进程在」不等于「Agent 已注册」。必须真正打开一次 WPS 文字并加载察元，外部客户端调用文档工具时才有活动文档上下文。只开 sidecar、不开 WPS，常见报错是 WPS 离线或 Agent 离线。

察元设置里的 MCP 服务页可以刷新状态、复制连接信息、必要时手动启动本机服务。有 Spike 或自检的版本，用它确认 sidecar、Agent、活动文档三层状态，比只看端口监听更完整。

![察元设置MCP服务页在线状态](images/csdn-02-4.png)

### 端口占用与环境变量

默认端口 62588。若被其他程序占用，sidecar 起不来或 healthz 无响应。处理：查出占用进程，结束误启的旧实例，或按文档设置 `CHAYUAN_MCP_PORT` 后同步改客户端 URL。改端口后，所有 `.mcp.json`、Claude 注册项、培训手册里的地址都要一起改，只改一端必现连不上。

## 分层排错

### 第一层：进程与 healthz

本机访问 [http://127.0.0.1:62588/healthz](http://127.0.0.1:62588/healthz)。不通：查自启是否被杀软拦截、端口是否占用、是否装了包却从未触发自启。通：进入第二层。

### 第二层：WPS 与加载项

打开 WPS，确认察元入口可见。再调一次依赖活动文档的只读工具。仍离线：重载加载项或重启 WPS，避免旧版本路径残留。

### 第三层：客户端配置

核对服务名、URL、transport。常见误配：写成 `https`；漏了 `/mcp`；写成局域网 IP；误选 stdio；多写了 Token。改完重启客户端或刷新 MCP 列表。

### 第四层：工具列表与冒烟

列表里能展开文档相关工具后，先做只读冒烟：问当前活动文档文件名与大概字数，禁止改正文。通过后再做校对预览。校对失败且报 MODEL_NOT_CONFIGURED，转到模型文：[模型与供应商配置](./03-model-provider-setup-proofread.md)。那是模型层，不是 MCP 层。

## 多客户端共用同一端口

Claude Code、Cursor、Codex、OpenClaw、Hermes 可以同时配置指向同一 URL。正常情况下它们共用一份 sidecar，不会也不应每人再起一份。若开发态手动跑了 `npm run mcp:sidecar` 之类命令，可能与安装版抢端口，表现为间歇性失败。生产使用以安装包自启实例为准。

可选验证：

```
npx @modelcontextprotocol/inspector
```

连接到 [http://127.0.0.1:62588/mcp](http://127.0.0.1:62588/mcp) 查看工具列表，用于排除「只是 IDE 显示问题」。

## 和自动审查流程的衔接

MCP 连通只解决「工具够得着文档」。预览、确认写批注、确认替换仍要按人在回路执行，见：[预览批注替换工作流](./04-preview-comment-replace-workflow.md)。提示词见：[提示词库](./05-prompts-for-auto-review.md)。源码与字段级说明需要时对照 [https://github.com/zhgyuhuii/chayuan.git](https://github.com/zhgyuhuii/chayuan.git)。

把本机 MCP 配准，等于给所有支持 HTTP MCP 的客户端开了同一扇门。门后仍是 WPS 文档与确认门禁；门本身则应保持本机、可健康检查、无 Token、Streamable HTTP 这四条不变。

## 为什么默认绑 127.0.0.1

本机绑定是产品默认安全边界，不是临时省略。公文与合同正文经工具调用进出 sidecar 时，暴露面被收在当前登录会话。局域网同事若要共用，需要你们自己加隧道、反向代理或受控跳板，并单独做权限评估；那不属于默认安装范围。有人把 URL 改成机器局域网 IP 后发现连不上，是预期行为：监听地址没变，只是客户端指错了门。

远程桌面场景下，Claude Code 跑在远端会话里、WPS 也在同一会话时，127.0.0.1 仍然指向该会话本机，一般可用。若 Claude 跑在笔记本、WPS 跑在另一台办公机，则必须自建转发，并清楚文档会经过哪段网络。不要把「本机 MCP」理解成「办公室任意电脑都能连」。

## 与 stdio 型 MCP 的差别

不少开发者习惯用 stdio：客户端拉起一条本地命令，标准输入输出传 JSON-RPC。察元这条链路不是那种形态。sidecar 作为常驻 HTTP 服务存在，客户端只负责连 URL。若在配置里写了 command、args 去启动某个脚本，而忽略 url 字段，常见结果是列表里有服务但握手失败，或误启动了第二份开发态进程抢端口。正确做法是 transport 选 http，只填 `http://127.0.0.1:62588/mcp`。

Streamable HTTP 的细节以 Claude 文档与 MCP 规范演进为准。对使用者而言，记住三句话即可：用 HTTP 不是 stdio；URL 带 `/mcp`；先用 `/healthz` 看活没活。Inspector 适合在没有 IDE 时验证工具列表，避免「客户端 UI 显示已连接但其实没拉到工具」的误判。

## 安装包里的 sidecar 实际做了什么

安装察元 AI 文档助手 v4.0 时，安装器除了把加载项放进 WPS 文字，还会放下本机 MCP 二进制，并注册开机自启。Windows 常见写法是当前用户启动项；macOS 常见是 LaunchAgent；Linux 常见是用户级 systemd 单元。日常使用不需要再单独安装 Node.js，也不需要每次打开终端手动起服务。你要做的是：装完后至少打开一次 WPS，让加载项完成 Agent 注册，然后用浏览器访问健康检查确认在线。

若公司安全软件拦截了自启，会出现「昨天装完能用，重启后 Claude 全部失败」。先看 healthz，再看自启是否被禁用，最后才查客户端配置。把顺序反了，会在 `.mcp.json` 里浪费很长时间。开发人员若在仓库里又手动拉起一份 sidecar，可能与安装版抢同一端口，表现为有时通有时不通；培训现场应禁止混用开发态命令与安装版服务。

## 路径抄写的十种错法

下面这些错误在培训里反复出现，按出现频率排列。第一，把地址写成 `https://127.0.0.1:62588/mcp`，本机服务不提供该证书路径，握手失败。第二，漏掉路径，只写到端口。第三，把健康检查路径填进 MCP 配置。第四，端口抄成 6258 或 65288。第五，服务名写成 chayuan、wps-mcp 等简称，和文档、同事配置对不上。第六，误选 stdio 并填写一段启动命令。第七，填了 Bearer Token。第八，把 URL 改成局域网网卡 IP。第九，本机改过 `CHAYUAN_MCP_PORT` 却只改了服务端。第十，项目级与用户级配置各写一份且不一致，客户端实际读到的不是你正在改的那份。

排错时把客户端里最终生效的 URL 复制出来，与浏览器地址栏里能打开的 healthz 对照。不要凭记忆口述「应该差不多」。

## 工具列表大概长什么样

不同小版本工具名可能微调，但能力分组相对稳定：状态与健康类、文档打开与活动文档类、分段读取与定位类、批注类、替换与写回类、校对预览与写成批注类。第一次验收不必调用全部工具。只读冒烟用状态或读取类；审查预览用校对预览类；确认后再用批注与替换类。若列表为空，优先怀疑 transport 与 URL，而不是怀疑「产品没有工具」。

用 Inspector 看到工具但 Claude Code 里看不到时，重启客户端、检查是否连到另一个 MCP 配置文件、确认没有同名服务被禁用。多配置文件并存时，以客户端当前工作区实际加载的那份为准。

## 和防火墙、代理软件的关系

默认监听本机回环，一般不需要在防火墙上对局域网放行。反而要小心本机代理软件把 `127.0.0.1` 请求错误地送进代理池，导致健康检查异常或超时。若开启了系统代理，给本机回环地址加直连规则。公司终端管控若禁止本地监听高位端口，需要信息技术部门把 62588 列入允许清单，这与「对外网开放端口」不是同一审批。

## 远程与多机时的现实约束

察元默认形态是「文档所在的那台机器上跑 WPS 与 sidecar」。Claude Code 若跑在另一台机器，必须有人维护一条到 62588 的安全转发，并清楚正文会经过哪段网络。不要在演示稿里宣传「装完即可远程审任意同事电脑上的文件」。那是另一套运维方案。单机闭环足够覆盖大多数公文与合同校对场景。

## 验收记录怎么写

给科室留痕时，建议记录四行：healthz 访问时间与结果；MCP 服务名与 URL；客户端类型与版本；只读冒烟是否通过。不必贴全文对话。出了问题把这四行发给协助者，比只说「连不上」有效得多。若涉及模型错误，另附加载项自测是否通过，避免把模型问题记成 MCP 故障。

## 小结成可执行规则

规则一：服务名固定 chayuan-wps-mcp。规则二：URL 固定到本机 mcp 路径，先用 healthz 看活。规则三：transport 用 HTTP，不走 stdio，不填 Token。规则四：先开 WPS 再调文档工具。规则五：多客户端共用一份 sidecar，禁止乱起第二份。规则六：端口若变更，服务端与所有客户端同时改。按这六条配，本机 MCP 层可以稳定交给上层的预览与确认流程使用。

## 给信息技术部门的简短说明

若科室要把察元纳入终端标准环境，信息技术部门通常会问三件事：端口是否对外、是否需要密钥轮转、自启是否可管控。答案可以写得很短。端口默认只绑本机回环，不纳入对外放行；本机 MCP 不使用 Token 轮转模型，模型密钥在察元设置里按供应商管理；自启可用系统既有软件分发与启动项策略管控，卸载或停用加载项后应同步停止 sidecar，避免留下无主进程。把这三句写进内部说明，能减少把本机服务误当成「又一个要备案的公网接口」。
