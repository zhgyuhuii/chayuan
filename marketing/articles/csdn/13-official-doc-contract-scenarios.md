# 公文与合同自动审查场景：提示词、批注与确认写回

公文和合同最怕两件事：表面错字漏改，以及结构要素缺失却在会签末段才发现。察元 AI 文档助手 v4.0 把本机 MCP（`chayuan-wps-mcp`，`http://127.0.0.1:62588/mcp`）交给 Claude Code、Codex、OpenClaw、Hermes 等客户端后，可以用自然语言做「初筛」：先出问题列表，你确认后再写批注或改字。它不能替代法制部门或文秘终审，但能把明显错别字、标点、常见缺项提前钉在稿面上。

本文给可复制提示词、分场景操作顺序、表格与长文注意点。客户端怎么接见 [./12-claude-codex-openclaw-hermes.md](./12-claude-codex-openclaw-hermes.md)；确认与安全边界见 [./14-confirm-security-localhost.md](./14-confirm-security-localhost.md)；错误码见 [./15-errors-troubleshooting-handbook.md](./15-errors-troubleshooting-handbook.md)。MCP 概念背景可参考 [modelcontextprotocol.io](https://modelcontextprotocol.io/)；产品入口见 [aidooo.com](https://aidooo.com)。

## 开工前固定三条纪律

### 活动文档要对

智能体操作的是 WPS 里当前活动文档。会签稿、合同底稿、历次修订稿同时开着时，先切换到要审的那一份，或明确让工具打开指定路径并激活。审错文件比审不出错更麻烦。

### 先预览，再 confirmed

写批注、替换、脱密等变更需要 `confirmed=true`。对话里对应你的一句「确认写批注」或「确认替换」。未确认会收到 `CONFIRMATION_REQUIRED`。脱密还要你本人提供还原密码，客户端不得编造。

### 模型要先在加载项里跑通

MCP 在线不等于校对可用。若返回 `MODEL_NOT_CONFIGURED`，先到察元设置配对话模型（含内网 Ollama，见 [./11-offline-ollama-intranet-review.md](./11-offline-ollama-intranet-review.md)），用加载项内检查验证，再让外部客户端上强度。

![审查前检查：活动文档标题、healthz、模型已选](images/csdn-13-precheck.png)

## 通用开场白（公文合同都适用）

```text
你通过 chayuan-wps-mcp 操作当前 WPS 文档。
1）先 dryRun/预览，列出问题：原文片段、问题类型、修改建议、大致位置；
2）不要改正文，不要写批注，直到我明确确认；
3）我回复「确认写批注」后，把采纳的条目写成批注，钉在具体文字上；
4）表格内错误必须钉在单元格文字上；
5）没有「确认替换」禁止改正文；涉密与法律结论以人工为准。
```

把这段放进客户端系统说明后，下面的场景提示词可以只写差异部分。

## 场景一：公文结构与体例

### 目标

检查标题、主送、正文层次、落款、附件说明等是否缺项或明显错乱；同时扫一遍错别字与标点。体例问题多用批注讨论，少直接改字。

### 提示词

```text
按公文习惯检查当前文档：
- 标题、主送机关、正文层级标题、落款单位与日期、附件说明是否缺项或位置异常；
- 序号是否跳号、层级是否混乱；
- 错别字、同音别字、中英文标点混用、引号书名号是否配对。
先输出问题列表，按「结构缺项 / 序号层次 / 错别字标点」分组。不要写批注，不要改正文。
```

确认后：

```text
确认写批注。结构类批注写明缺什么、建议补在何处；错字类批注写原文和建议改法。
```

### 人工复核点

- 「主送是否正确」模型可能不懂组织沿革，只把「疑似缺主送」标出来，由文秘定夺。  
- 密级、份号、紧急程度等版式字段，以本单位公文模板为准，不要让模型按互联网常识乱补。  
- 批注锚点应落在标题行或缺项附近，而不是文末总评一句。

## 场景二：合同要素与风险清单

### 目标

对合同做要素初筛：当事人、标的、价款或报酬、期限、违约责任、争议解决等是否出现；前后金额、日期、甲方乙方称谓是否打架。法律效力结论必须人工给，模型只负责「列出疑点」。

### 提示词

```text
对当前合同文稿做要素与一致性初筛：
1）是否出现合同主体（甲乙方或多方）、标的、金额或计价方式、履行期限、违约责任、争议解决方式；
2）文中金额大小写、日期、当事人名称是否前后一致；
3）明显错别字与标点问题。
输出「要素缺失或不明」「一致性冲突」「文字问题」三组列表。每条给原文摘录。只预览，不写批注，不改正文。
```

高风险条目单独加一轮：

```text
在上一轮列表基础上，把可能影响价款、期限、违约金计算的条目置顶，并说明为什么危险。仍不要改文件。
```

确认写批注时：

```text
确认写批注。要素缺失类批注写「未见某某条款，请业务确认」；冲突类写清两处原文；不要直接改条款文字。
```

### 人工复核点

- 缺条款不等于一定无效，可能在附件或补充协议；批注应引导人去查，而不是下判决。  
- 数字冲突必须人眼对底稿与审批单。  
- 需要改字时按条确认替换，避免一次「全部自动改」把谈判口径改没。

## 场景三：错别字、同音字与表格

### 公文通知、纪要

```text
检查错别字、同音别字（的地得、象像、做作）、成语误用，以及专有人名地名单位名前后是否一致。先预览列表。
```

### 合同附表、价款表

```text
重点检查表格单元格里的错别字、金额与单位。批注必须钉在单元格具体错字或错误数字上，不能只在表后总评。先预览。
```

确认：

```text
确认写批注。第 3、6、8 条先写批注；第 6 条金额冲突不要改正文，留待人工。
```

表格锚点失败时，常见错误码是 `LOCATE_NOT_FOUND` 或 `LOCATE_MISMATCH`：让智能体重新读取该单元格原文，再带一致的 `originalText` 写批注。不要反复 force 替换。

## 场景四：长文分块审查

### 何时会碰到 DOCUMENT_TOO_LARGE

一次拉取过大文档内容时，服务可能返回 `DOCUMENT_TOO_LARGE`（未强制且体量过大）。正确策略是分块，而不是默认 `force=true`。

### 提示词

```text
当前文稿较长。请按段落或分块读取，每块做错别字与标点检查，最后合并去重输出总表。
不要一次拉取全文。不要写批注，等我确认。
```

公文可按「版头 / 正文 / 附件说明」切；合同可按「总则 / 商务条款 / 法律条款 / 附件附表」切。每块审完再合并，避免上下文丢失导致前后术语不一致漏检——需要时再开多文档交叉校对任务。

![长文分块审查进度与合并后的问题总表](images/csdn-13-chunked-review.png)

## 场景五：多文档对照（制度 / 合同套件）

```text
打开以下路径的文档并依次检查（路径以我给出的为准）：
1）主合同；2）补充协议；3）附件报价表。
交叉核对当事人名称、金额、期限是否一致；不一致处列入列表，注明分别出自哪份文档。只预览。
```

操作注意：

- 每次写回前确认活动文档是不是你想改的那份。  
- 建议只在主合同上写批注，补充协议的问题在列表里写清来源，防止批注写串文件。  
- Agent 离线时先恢复 WPS 与 healthz，再继续多文档指令。

## 场景六：保密与敏感信息（初筛）

```text
检查当前材料是否出现疑似身份证号、手机号、银行卡号、详细住址等敏感信息，用列表标出位置与类型。只预览，不脱密，不改正文。
```

若业务上要做脱密写回：必须走预览 → 你提供密码 → `confirmed=true` 的 apply；还原同样要密码。禁止让模型「随便设一个密码」。详见第 14 篇。

外链资料与制度条文对照时，以单位知识库或本机资料为准；公网检索不是内网公文场景的默认依赖。

## 建议的半天培训流程

### 准备工作（30 分钟）

安装察元 v4.0；healthz 在线；模型可用；Claude Code 或 OpenClaw 已接 `chayuan-wps-mcp`。准备一份故意含错的公文样例和一份合同样例（脱敏）。

### 实操（90 分钟）

1. 公文结构提示词 → 预览 → 确认写批注 → 抽查锚点。  
2. 合同要素提示词 → 预览 → 只批注不改条款。  
3. 表格错字提示词 → 确认批注钉在单元格。  
4. 人为制造未确认写回，演示 `CONFIRMATION_REQUIRED`。  
5. 对长样例触发分块，演示如何避免 `DOCUMENT_TOO_LARGE`。

### 验收标准

- 学员能独立说出端点与服务名。  
- 学员能不看稿完成「预览 → 确认写批注」。  
- 学员遇到 `MODEL_NOT_CONFIGURED` / `WPS_AGENT_OFFLINE` 知道回哪里查。  
- 学员不把自动审查结果当作可印发的终稿。

## 提示词维护建议

### 按单位模板沉淀

把「本单位公文必检项」「本合同类型必检项」写成第二段提示词，接在通用开场白后。例如学校公文加「文号格式」；工程合同加「质保金与工期」。不要指望通用模型记住你们红头文件细则。

### 版本与客户端

提示词与客户端无关，四个客户端可共用。模型更换（例如从云端换成 Ollama）后，用同一份样例回归：问题列表是否仍覆盖故意埋下的错误。回归失败先查模型，再查提示词是否被改短过度。

Claude 侧 MCP 用法参见 [Claude Code MCP 文档](https://code.claude.com/docs/en/mcp)。仓库连接说明见 [docs/mcp-connection.md](https://github.com/zhgyuhuii/chayuan/blob/main/docs/mcp-connection.md)。

## 可直接归档的提示词卡片

把下列卡片存进内部知识库，文件名用场景编号，避免聊天记录里到处找。

### 卡片 G-01 公文综合初筛

```text
按本单位公文习惯检查：标题、主送、层级序号、落款、附件说明；并检查错别字与标点配对。
分组输出：结构、序号、文字。只预览。
```

### 卡片 G-02 会议纪要

```text
检查纪要中的出席/列席是否前后一致，决议条款序号是否连续，时间地点是否有明显矛盾，错别字一并列出。只预览。
```

### 卡片 C-01 合同要素

```text
检查主体、标的、价款或计价、期限、违约责任、争议解决是否出现；金额与日期是否前后冲突。三组输出。只预览。
```

### 卡片 C-02 补充协议对照

```text
以当前活动文档为补充协议，对照我指定的主合同路径，列出名称、金额、期限不一致项，注明两侧原文。只预览，不写回主合同。
```

### 卡片 T-01 表格数字

```text
只检查表格中的金额、数量、单位与错别字；批注必须钉单元格。先预览。
```

使用时在卡片前粘贴通用开场白；确认阶段另发「确认写批注」或「确认替换第 x 条」。不要把确认写进卡片正文，以免无人值守误触发。

## 审查结果怎么交给下一岗

### 批注交给会签

自动审查写的批注应能让下一岗看懂：原文、问题、建议。避免只写「有误」两个字。会签人可以在 WPS 里回复批注，这比把问题列表留在外部聊天更好追溯。

### 列表交给会议

若本轮只预览、不写批注，把列表粘贴进审议邮件时，先脱敏。内网邮件系统若给出站审计，注意列表里可能含条款原文。

### 终稿纪律

任何「模型已检查完毕」都不能单独作为印发依据。印发前仍走人工校对与审批。产品错误码与门闩不能替代公章流程。

## 小结

公文与合同自动审查，落地关键是「可核对的问题列表 + 人确认后的批注」，不是一键生成可盖章文本。把缺项检查、要素核对、错字表格、长文分块拆成提示词卡片，遵守 `confirmed` 与活动文档纪律，察元 v4.0 的本机 MCP 才能在编校和法务初筛里稳定干活。更多端口安全与错误码，继续读第 14、15 篇。
