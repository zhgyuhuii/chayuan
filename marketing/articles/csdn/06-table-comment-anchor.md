# WPS 表格批注锚点：为什么会挂整格，以及怎么让 Claude 钉在错字上

表格里的错别字比正文更难审。业务同事打开批注窗格，如果气泡挂在整格、整行甚至段尾空白上，审查结果会被当成不可信。察元在 v4 对表格锚点做了专门加固，但外部智能体（尤其是 Claude Code 经本机 MCP）如果指令写得笼统，仍然容易产出「看起来改了、落点却不对」的批注。本文只讲表格锚点：现象、原因、指令写法、验收标准，以及和预览确认流程怎么配合。

服务名用 `chayuan-wps-mcp`，本机入口是 `http://127.0.0.1:62588/mcp`，健康检查是 `http://127.0.0.1:62588/healthz`。安装与接通总览见 [全生命周期安装与审查](./01-lifecycle-install-to-claude.md)；写批注前的确认策略见 [确认策略与安全边界](./14-confirm-strategy-safety.md)。

## 先复现：什么叫「挂整格」

### 合格落点长什么样

在 WPS 文字里打开含表格的测试稿，某一格故意写「永鹅」应为「咏鹅」。校对完成后：

1. 批注气泡的高亮范围只覆盖「永鹅」两字，或至少覆盖该词，不覆盖整格其余空白。
2. 批注窗格里的「原文」字段与单元格中可见错字一致。
3. 同格有多个词时，每个问题各自钉在对应子串，而不是五个问题共用一个整格锚点。

### 不合格落点长什么样

1. 高亮铺满整个单元格，含尾部看不见的单元格结束标记。
2. 高亮落在下一列、下一行，或落在表外正文。
3. 批注写在了段落末尾，表格本身没有任何标记。
4. dryRun 列表里的原文对，写成批注后 Scope 被 WPS 扩到整格。

第三种和第四种最容易在联调时被漏掉：列表看起来正确，写回后肉眼一扫才发现锚点漂了。表格验收必须以 WPS 里的高亮为准，不能只看 Claude 对话里的文字列表。

## 为什么表格比正文更容易漂

### 单元格尾部有不可见标记

WPS / Word 对象模型里，单元格文本范围常带 `\u0007` 一类单元格或行结束标记，段落则有 `\r`。如果定位算法用「块起点 + 纯文本下标」硬算 Range，下标会把这些标记算进去或漏掉，结果 Range 被扩到整格。察元内部对此的处理路径是：Find 锁定原文，裁掉单元格与段尾标记，再 Select，然后 `Comments.Add`，最后回读 Scope；Scope 被扩到整格时再做 Selection 重绑。外部智能体看不到这些细节，但会间接受益——前提是传入的原文片段足够短、足够唯一。

### chunk 下标不等于文档绝对坐标

长文或大表走 `document_chunks` 时，chunk 内的字符下标不能直接当成整篇文档的绝对偏移。表格空段、单元格标记都会造成漂移。正确做法是带着 chunk 返回的 `start` / `end` 与 `originalText` 去定位，或走 `document_locate` / 校对工具链，而不是自己拼绝对坐标。长文分块策略见 [长文档分块审查](./07-long-doc-chunk-review.md)。

### 指令只说「检查表格」不说「钉在错字」

模型倾向把「单元格」当成最小语义单位。你不写约束时，它可能一次给整格加一条批注，文案写「此格有误」。对业务审查来说这等于没标位置。必须在开场白和单次指令里写死：批注钉在单元格里的具体错字上，不要挂到整格。

## 给 Claude Code 的指令模板

确认 `healthz` 返回 online，Claude 已挂上 `chayuan-wps-mcp` 后，用下面模板。MCP 协议说明可对照 [Claude Code MCP 文档](https://code.claude.com/docs/en/mcp)。安装包与发行说明见 [GitHub Releases](https://github.com/zhgyuhuii/chayuan-wps-releases) 与官网 [aidooo.com](https://aidooo.com)。

### 开场白（表格优先）

```text
你通过 chayuan-wps-mcp 操作当前 WPS 文档。
1）先做校对预览（dryRun），重点检查表格单元格内的错别字与标点。
2）每条问题必须给出：所在表/行/列（若能判断）、原文子串、建议改法。
3）等我回复「确认写批注」后再写批注。
4）批注必须钉在单元格内的具体错字上，禁止挂到整格、整行或段尾标记。
5）没有「确认替换」禁止改正文。
```

### 单次表格专项指令

```text
重点检查表格单元格里的错别字，批注必须钉在具体错字上，不要挂到整格。
先预览问题列表，不要写批注。
```

### 确认写回

预览列表人工过目后回复：

```text
确认写批注。
```

需要改正文时再按条确认：

```text
按第 2、5 条确认替换，其余只保留批注。
```

写操作在未确认时会要求确认或只返回预览，这是设计，不是故障。相关工具包括 `document_add_comment`、`proofread_apply_comments`，均需要明确确认才会落盘。

## 推荐工具路径（外部 LLM 推理）

### 路径 A：校对工具快捷链路

1. `wps_status` 或浏览器打开 `http://127.0.0.1:62588/healthz`，确认 online。
2. `proofread_run`（dryRun）拿到 issues。
3. 人工确认后 `proofread_apply_comments`（带 confirm）。
4. 在 WPS 批注窗格抽查表格锚点。

适合常规错别字、标点。模型未配置时会报 `MODEL_NOT_CONFIGURED`，先回加载项设置配对话或校对模型。

### 路径 B：分块 + 定位 + 批注

1. `document_meta` 看字数与是否建议分块。
2. `document_chunks` 按块读，不要对大表默认 `document_get_text`。
3. 外部模型在块内找错字，产出带 `originalText` 的条目。
4. `document_locate` 校验命中；歧义多命中时收窄原文子串。
5. `document_add_comment`（`confirmed: true`）或 `document_apply_ops` 预览后再确认。

路径 B 在合并单元格、嵌套表、表内再套段时更可控：你强制模型带短原文，定位失败会变成 `LOCATE_NOT_FOUND` / `LOCATE_MISMATCH`，比静默挂整格好排查。

### 路径 C：加载项内先自检

不经过 Claude，在察元「拼写与语法检查」对同一张测试表跑一遍。若加载项内批注能钉准、经 MCP 却挂整格，优先查指令与确认流程，而不是先怀疑安装坏了。加载项与 Claude 路径对比见 [加载项内置检查对比 Claude MCP](./10-addon-vs-claude-mcp.md)。

## 测试稿怎么造

用一张三行四列表即可，不要一上来就拿百页合同。

1. A2 写「永鹅」，预期改为「咏鹅」。
2. B2 写「的地得」混用一句短句。
3. C2 故意中英文逗号混用。
4. D2 留空，另写一条「不应为空」的检查指令做对照。
5. 表下再写一段正文错字，确认表内表外批注互不串位。

审查顺序：只读文件名与字数 → 表格专项预览 → 确认写批注 → 逐格点开高亮。若 A2 高亮正确而 B2 挂整格，把 B2 的原文子串再缩短，重新 locate 一次，不要整表重跑盲目加重试。

## 验收清单（建议贴到科室规范）

1. healthz 为 online；出现 `WPS_AGENT_OFFLINE` 时先开 WPS 与察元加载项，再刷新 MCP。
2. 预览列表条数与写回批注条数一致，或差异有说明（合并、去重、误报剔除）。
3. 抽查不少于 5 个表内批注，高亮均落在具体错字。
4. 无「整格一条」且原文为空或仅为空白的批注。
5. 未口头或书面「确认替换」前，正文与单元格文字未被改写。
6. 另存为「原名-表校-日期」后再交下一环节。

四级连通验收见 [healthz 与四级验证](./09-healthz-four-level-verify.md)。多文档交叉时，先把每份文档的表格锚点规则写进开场白，再谈术语对齐，见 [多文档交叉校对](./08-multi-document-cross-proofread.md)。

## 排错对照表

| 现象 | 优先检查 | 处理 |
| --- | --- | --- |
| 批注挂整格 | 指令是否写死钉错字；原文子串是否过长 | 缩短 originalText；重跑 locate；不通过则不要确认替换 |
| 批注落邻格 | 合并单元格、隐藏列 | 用可见文本再定位；必要时拆步只审一张表 |
| 列表有、批注无 | 是否回复确认写批注；是否 CONFIRMATION_REQUIRED | 明确确认后再 apply |
| 工具报 WPS_AGENT_OFFLINE | WPS 未开或加载项未加载 | 打开文档，刷新 healthz |
| 校对报 MODEL_NOT_CONFIGURED | 察元设置未配模型 | 先配模型，加载项内自检通过后再走 Claude |
| DOCUMENT_TOO_LARGE | 对大表全文 get_text | 改用 document_chunks |

## 和正文校对的分工建议

正文可以一次预览较多条目；表格建议「先表后文」或「表单独一轮」。原因很实际：表内锚点抽查成本高，和正文混在同一长列表里，人工更容易漏掉挂整格的条目。科室规范可以写成：

1. 第一轮：仅表格，确认写批注并抽查。
2. 第二轮：正文与标题。
3. 第三轮：表数与正文数字勾稽。

第三轮不必再纠结锚点形状，重点看数值是否一致。勾稽类问题用批注说明「正文第 X 段与表 N 第 R 行不一致」即可，锚点可以钉在正文数字或表内数字其中一侧，并在批注正文写清另一侧位置。

## 版本与能力边界

v4.0 起表格内错别字批注不再盲信 `chunkStart + 文本下标`，而是 relativeRangeMap、live 文本复核，以及 Find → 裁标记 → Select → Comments.Add → 回读 Scope 的路径。这降低了挂整格概率，但不等于「任何模糊指令都能钉准」。外部 LLM 仍可能给出过长原文、错误原文或跨格原文；定位失败时应停下来改指令，而不是反复 `confirmed: true` 强行写回。

涉密表、名单表、金额表在写批注后仍要人工复核。自动审查解决的是「找得到、标得准、改得可控」，不是替代签发。发行渠道与版本号以 [aidooo.com](https://aidooo.com) 与 [chayuan-wps-releases](https://github.com/zhgyuhuii/chayuan-wps-releases) 当前页为准。

## 可复制的日常话术（精简版）

把下面两句固定进团队开场白即可覆盖大多数表格场景：

```text
重点检查表格单元格里的错别字，批注必须钉在具体错字上，不要挂到整格。
先预览；我确认写批注后再写；没有确认替换不要改正文。
```

需要打开指定文件时再加：

```text
用 document_open 打开指定路径，确认其为当前活动文档后再审表。
```

多文件切换见多文档篇。提示词全集与开场白变体见 [提示词与开场白](./05-prompt-and-opening.md)。

## 合并单元格与嵌套表

### 合并单元格

横向或纵向合并后，对象模型里的「格」与肉眼看到的「格」可能不一致。定位时若原文跨越合并边界，Find 可能落到合并区域的主单元格，高亮看起来像整块色斑。处理原则：

1. 指令要求一次只标一个可见错词，不要把整句跨多格原文塞进一条批注。
2. 预览列表里写清「第 r 行可见文本」。
3. 抽查时用键盘在表内逐格移动，确认高亮跟着错字走，而不是整块合并区常亮。

### 表内再套段落

有的材料在单元格里敲了多段，甚至再贴小表。此时 chunk 边界更容易切在标记附近。遇到定位反复失败，把该表复制到新建文档单独审，确认锚点策略没问题后，再回原件按同样原文子串写批注。这比在百页稿里死磕一次失败更省时间。

## 与 proofread 快捷链路的配合细节

`proofread_run` dryRun 返回的 issues 通常已带原文片段。应用到批注前，建议在对话里要求 Claude 输出一张「将要写回」的子集表：序号、原文、建议、是否表内。你删掉不信任的行，再确认写批注。不要因为快捷链路省事就跳过子集确认——表内误报写成批注后，清理成本高于多问一句。

若 issues 原文已经是整格文本，先让 Claude 把原文收缩为最小错词再 apply。收缩失败就改走 `document_locate` 人工指定子串。产品侧会尽量裁标记，但整格原文进定位，失败面仍然更大。

## 培训时怎么讲清楚

给业务同事演示，不要先讲 `\u0007`。只演示三屏：

1. 错误示范：挂整格的批注，业务说「这没法用」。
2. 正确指令：念出「钉在具体错字上，不要挂到整格」。
3. 正确结果：高亮只盖两字，批注窗格原文一致。

技术同事再补：healthz、确认写批注、`WPS_AGENT_OFFLINE`。两层听众分开，避免一上来就讲对象模型导致业务关机。

现场练习限时十五分钟：每人改开场白一行，跑同一张三行四列表，互查对方高亮。不合格的常见原因几乎总是同一句——指令里删掉了「不要挂到整格」。

## 与替换写回的顺序

表内错字更建议「先批注、后替换」。原因：

1. 替换改的是单元格文本，审阅痕迹弱于批注。
2. 锚点若仍漂，替换可能改到邻格或留下残字。
3. 业务对表内数字、姓名更敏感，需要看得见的建议再决定。

顺序固定为：预览 → 确认写批注 → 抽查高亮 → 按条确认替换。任何一步高亮不合格，停止替换，回到定位。相关确认话术与安全边界见确认策略篇；本篇只强制一点：表内替换的前置条件是锚点抽查通过。

## 小结（给实施同事）

表格批注质量由三件事共同决定：产品侧锚点路径、模型侧原文粒度、流程侧预览确认。察元把第一件事做重了；你要把第二、三件事写进 Claude 指令和科室验收单。抽查时只看一件事：高亮是不是盖在错字上。盖住了，列表再漂亮也算过；盖不住，先别进替换，也别把问题推给「模型不行」——多数时候是指令没写死，或确认写回前没有做表内目视检查。把「钉在具体错字上，不要挂到整格」写成不可删的默认句，再配上三行四列测试表，表格审查才能从偶发成功变成可交接的流程。
