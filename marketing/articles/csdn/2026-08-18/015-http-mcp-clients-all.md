# Cline、Hermes、OpenClaw 都能连：HTTP 型 MCP 客户端全适配

后台被问得最多的一类问题是："我用的是 Cline / Hermes / OpenClaw，能连察元的 WPS 文档服务吗？"

统一回答：能。而且这个"都能连"值得单独写一篇——不是我们挨个给每个客户端做了适配，而是所有这些客户端都说了同一种"方言"：Streamable HTTP。MCP 生态爆发之后客户端百花齐放，但如果服务端选对了传输形态，适配成本可以低到忽略不计。

## 为什么 HTTP 型 MCP 天生全适配

MCP 常见两种形态：stdio 是客户端把服务当子进程拉起来，通过标准输入输出通信，和进程环境绑得很紧；Streamable HTTP 则是服务自己跑着，客户端拿一个 URL 通过 HTTP 连。后者的好处一目了然：

客户端不用关心服务怎么启动、用什么运行时——察元的 MCP 服务是单文件二进制，安装脚本装完就注册开机自启，不需要 Node.js，没有 stdio 管道那些琐碎事。

服务始终只有一份，谁需要谁来连。WPS 加载项用它，外部 Agent 也用它，不存在每个客户端各拉一套进程的情况。

接入动作高度一致：填 URL，完事。察元的服务地址固定是 `http://127.0.0.1:62588/mcp`，只监听本机回环，无 Token、无命令、无 stdio。

现在 MCP 客户端几乎一个月冒出好几个新的，如果每个都要服务端单独适配一遍，维护成本会跟着客户端数量线性上涨。HTTP 型把这件事变成了"一次实现、零适配"：新客户端只要支持 MCP 的 HTTP 传输，填上地址就能用，服务端一行代码不用改。站在 2026 年看，选 Streamable HTTP 是有远见的。

## 各家客户端接入盘点

Claude Code，一条命令搞定：

```bash
claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62588/mcp
```

OpenAI Codex CLI，编辑 `~/.codex/config.toml`：

```toml
[mcp_servers.chayuan-wps-mcp]
url = "http://127.0.0.1:62588/mcp"
```

Cursor，项目级 `.cursor/mcp.json`，写法与通用 `.mcp.json` 相同，或者走 设置 → MCP → Add 界面。

Cline、Hermes、OpenClaw：在各自的 MCP 设置里新建服务，类型选 HTTP 或 Streamable HTTP，URL 填上面那个地址，保存即可。Cline 这类常驻编辑器的开源 Agent，配置入口都在 MCP 设置页里；Hermes、OpenClaw 这些新锐客户端同理——只要设置里有 HTTP 型可选，就能连。没有任何一家需要写启动脚本或装额外运行时。配完之后的表现也都一样：能列出工具清单、能调 wps_status 看健康、能读文档元信息，就算接通了。换客户端的成本几乎为零，这也是 HTTP 形态最实在的好处：服务不动，客户端随便换。

## 拿不准就用 Inspector 通用验一遍

客户端千差万别，验证工具是统一的。官方的 MCP Inspector 一行命令拉起：

```bash
npx @modelcontextprotocol/inspector
```

在界面里传输类型选 Streamable HTTP，地址填 `http://127.0.0.1:62588/mcp`，点 Connect，就能看到 46 个文档工具的清单，还能手动调用测试——先点 wps_status 看分层健康，再试试只读类工具，服务侧的能力一目了然。

## 连不上时的排查顺序

这套顺序的思路是从服务到协议再到客户端，逐层排除，每一步都有明确的通过标准。

第一步，healthz：浏览器开 `http://127.0.0.1:62588/healthz`，不通就是服务侧问题，先检查安装和自启。第二步，Inspector：能连上说明协议层没问题。第三步，查客户端配置：最常见的错误是把类型选成了 stdio，或者在配置里找不到 URL 字段——回到"新建 → 选 HTTP → 填 URL"这三步检查。第四步，重启会话：不少客户端只在启动时读一次 MCP 配置。按这个顺序走，问题基本都能定位到具体哪一端；定位准了，去社群求助时也能把现象描述清楚，少一轮来回。

## 一点使用建议

客户端不必专一，按场景分工反而顺手：写代码时 Cursor、Claude Code、Codex 顺手就把文档批注干了；日常桌面场景不依赖任何外部 Agent，直接用 WPS 里察元的 29 个内置助手；要折腾自动化编排再上各类 CLI 工具。与其纠结哪个客户端最强，不先把服务端这头配稳。同一个本机服务，谁顺手用谁，反正地址就一个；唯一需要固定的，是跑着 WPS 和服务的那台机器——文档在那，根就在那。

边界提醒：多客户端切换着用没问题，但写操作请一个会话一确认。察元的 preview 和 confirmed 机制会兜底，AI 没得到确认就只能给方案不能落盘——工具再多、客户端再花，最后定稿的那个人还得是你。
