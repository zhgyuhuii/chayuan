# 脱密还能复原：占位符替换的可逆脱敏流程

对外提供材料，最磨人的环节是脱敏：把人名、证件号、账号换成占位符。手工换的问题在于换了就找不回来——外发版本改到第三轮，有人问一句"这个【人员A】原来是谁"，你就得翻原始文档人肉对，版本一多连自己都怀疑对错了行。这篇记录我用察元AI文档助手做可逆脱敏的完整流程。它的思路一句话：替换成占位符的同时保留映射关系，需要时凭密码复原。

先讲工具。察元的本机 MCP 服务里有一组脱密工具，四个：declassify_status 查状态、declassify_preview 做预览、declassify_apply 正式替换、declassify_restore 复原。外部智能体（Claude Code、Cursor、Codex 这类）接上 http://127.0.0.1:62588/mcp 这个地址就能调用。整个服务只监听 127.0.0.1，流程全程在本机完成，这也是数据安全不出域最直接的实现方式——不是承诺出来的，是网络结构决定的。

**第一步：查状态。** 让智能体先跑 declassify_status，确认当前文档的脱密状态——是原始文档、已脱密还是已复原，别在错的版本上开工。这一步几秒钟，能省掉后面所有糊涂账。

**第二步：预览。** 这是整个流程里我最赞许的设计：declassify_preview 只展示替换效果，不写盘。哪些词会被换成什么占位符，先出一张预览清单看清楚。我的习惯提示词：

```
先做脱密预览，列出会被替换的关键词和对应占位符，不要写盘，我确认后再执行
```

预览阶段常能发现要调整的地方：有的词不该换（比如本来就公开的人名），有的词该换但粒度不对（换得太碎，复原时对不上号）。趁不写盘的时候调，成本为零。

**第三步：正式替换。** declassify_apply 有三道门槛：确认、密码、关键词列表。密码是复原的钥匙，设一个只有经办人知道的。替换执行后，外发版本里就是【姓名1】【证件号2】这样的占位符，正文可读，身份不露。

**第四步：复原。** 材料外发后如果需要回到原始版本，declassify_restore 凭密码把占位符换回原文。这就是"可逆"的价值：外发版改一百轮，底稿始终能对上号，不用再维护一套"对照表"文档。

适用场景说几个真实的：对外提供典型案例材料，当事人姓名和证件号脱成占位符；评优申报材料里同事的身份证号；调研报告引用的内部访谈记录。共同点是"内容要出去、身份要留下"，而且外发版后续大概率还要改——只要会改，可逆就比一次性删改强。

配合另一条流程用更顺：先用敏感信息批注定位，把疑似位置和业务判断做完，确定要脱敏的关键词列表，再进脱密预览，最后 apply。定位管"脱什么"，脱密管"怎么脱"，两条线分开走，每一步都有确认点。正式替换前我还有个习惯：让智能体先另存一份当天的底稿再动手，版本在手，心里不慌——外发材料和底稿的对应关系，是这套流程真正要守住的东西。

两个实操提醒。其一，关键词列表自己定，别让 AI 自作主张扩列表——机器觉得"敏感"的词未必是你想脱敏的词，预览里看清每一条再确认。其二，密码丢了复原就麻烦，经办人岗位调整时，把这套流程和密码管理写进交接单，别让可逆流程卡在找不到密码上。另外，脱敏之外文档本身的规范问题——版本、留痕、修订痕迹——加载项里有"文档审计助手"（书签级审计）可以配合看，但真正的兜底还是发文制度。

边界必须说明白：这套流程是文档层面的脱敏辅助，不等于保密审查。一份材料该不该脱敏后外发、脱到什么程度，要按保密要求和审批流程定——辅助工具，不替代定密程序和人工保密审查，这句话在脱密场景同样成立。

用了半年，我最大的感受是：脱敏这件事从"换完就忘"变成了"换了能回"。占位符不再是单行道，经办人换人也接得住，这就是流程该有的样子。
