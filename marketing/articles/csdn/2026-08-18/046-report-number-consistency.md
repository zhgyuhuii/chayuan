# 汇报材料数字打架：勾稽检查替你抓口径

上个月我们一份汇报材料被上级退回来了。退回理由很具体：正文写"全县新增市场主体 1200 余户"，附表分乡镇合计是 1247 户，而材料第二部分推进情况里又出现了"1236 户"。三个数各自都有来历——一个是年初目标数，一个是统计站最新月报数，一个是业务科室台账数——但它们同时出现在一份材料里，而且没作任何说明。

被退回那天下午，我把材料核了三遍才把三个数的出处理清。复盘的时候我意识到：这不是粗心，是流程缺陷。稿子改到第八稿，谁还记得第一稿里的数？肉眼校对根本防不住数字打架。各单位都在聊政务大模型，其实先把"数字对不对得上"这种小事交给机器，就是最实在的落地。从那以后我给自己立了规矩：凡带数表的稿子，上报前必跑数字勾稽。工具是 WPS 里的察元加载项，提示词就一句：

```
核对数表与正文数字是否一致（合计、百分比）
```

## 数字打架的三种典型

复盘下来，材料里数字出问题，基本就三种形态。

第一种：正文与表格不一致。正文引用的是旧版数，表格更新了，或者反过来。改稿改到最后，正文改了表格没跟着改，最常见，也最伤——领导通常先看表。

第二种：分项合计与总数对不上。乡镇数加起来和全县数差一截，可能是四舍五入的尾差，也可能是漏了一个单位。差多少算尾差、差多少算出错，要有个判断。我这边的习惯是：差额能解释清楚的，注明"因四舍五入，分项合计与总数略有出入"；解释不清的，退回重报。

第三种：同一指标前后口径不一。在册数与新增数、时点数与时期数、含与不含某个专项，混着用。这种最隐蔽，机器也最难判——它需要知道业务口径，而这恰恰是 AI 的边界，只能靠人来把关。

## 我现在的勾稽流程

第一步，终稿后先跑上面那条勾稽提示词，让它把正文数字和数表数字逐一对照，不一致的用批注标出来。表格里的数它会用切片读的方式按列核对，合计行、百分比列是重点盯防对象。表格的读法有讲究：先读表头再按列拉数，数量和百分比分开核——MCP 工具里有对应的表头读取、按列读取能力，用 Claude Code 这类外部智能体的按列拉就行，加载项用户不用操心底层细节。

第二步，涉及多个来源材料的，再加一条多文档交叉：

```
打开目录下这几份文档，交叉检查错别字与术语是否一致
```

术语一致这条对数字同样有用——同一个事项在几份材料里叫法不一，往往就对应着统计口径不一，顺着术语差异去追口径，经常一追一个准。

第三步，批注逐条人工裁决。机器告诉你"这里对不上"，为什么对不上、以哪个为准，必须回到数据来源去核：以统计站月报为准的，标注数据来源和时点；业务口径调整的，加脚注说明。裁决完改完，再复跑一遍勾稽，确认问题清零才上报。

这套流程适合谁？经常报材料的综合科、统计口、写汇报材料的业务科室，频率越高越划算——立一次规矩，省无数次返工。

## 几句实话

用了半年，勾稽检查抓出的问题不少，但要说句公道话：它抓的是"对不上"，不是"错了"。哪个数是对的、口径怎么统一，永远要人去核实。AI 辅助、人工核对为准，这八个字才是这个功能的完整用法。指望着把材料丢给 AI 核一遍就签字上报，等于把自己该负的责任也一并交了出去，真出了问题，追责追的是签字的人，不是工具。

被退回那次的教训，后来变成了科室的规矩：数字必须注明来源和时点，勾稽不过不上报。规矩比工具重要，但工具让规矩执行得起——这才是技术该待的位置。
