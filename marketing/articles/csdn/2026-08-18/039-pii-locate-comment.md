# 身份证、手机号、银行卡：敏感信息批注定位实战

前两周接了个活：一份二十多页的人员情况说明，正文里散落着身份证号、手机号，几张补贴发放表还带着银行卡号。上报版本要求把这些信息处理掉。两万多字的文档肉眼找，找完眼睛都是花的。这篇记录我用察元AI文档助手加 MCP 智能体做批注定位的实战过程。

需求先拆清楚：不是一删了之，是先定位、再逐条判断。有的号码是业务必需——联系人手机号要保留，不然上级找不到人；有的必须处理——普通人员的身份证号要打码。所以第一步不是替换，是让每个疑似位置都有一枚批注钉着，人再逐条决定。批注这个形式还有个好处：判断留痕，事后说得清哪条是谁定的。

流程三步。

第一步，全文扫描。在 WPS 里打开文档，一句话发起：

```
查找疑似身份证号、手机号、银行卡号并批注
```

背后智能体干的事是这样的：察元的 MCP 服务提供了 document_list_paragraphs（带锚点）和分块读取工具，长文档会建议分块，两万字属于正常范围；模型逐段扫模式——18 位数字串、11 位手机号格式、银行卡号特征，发现疑似就调 document_add_comment 写批注。这个工具有确认门槛，不传 confirmed:true 只会返回待确认列表，不会动文档，扫完先给我一张清单过目。

第二步，人工复核批注。点开批注逐条看，重点是排误报：统计表里的固定电话、文件编号里的长数字串，偶尔会被误认成手机号或证件号。这一步顺带做分类：保留、打码、删除，直接在批注回复里记结论。

第三步，批量写回。判定完的位置要处理时，让智能体用 document_apply_ops 批量执行——替换和批注可以混合编排，一次最多 200 个操作，二十多页一轮跑完，不用一条条点。

误报的类型也值得先说一句，帮你建好预期：固定电话被认成手机号、十几位的统计期数被认成卡号、文号里的数字串被认成证件号，是三种最常见的误报。反过来，漏网的也有套路——号码中间加空格、加横线，证件号分段填在两个单元格，模式匹配就容易滑过去。所以复核阶段我对表格格外多看一眼，表格的行列结构最会藏这类变形。

整个流程跑完的产出是三样：一份带批注的原文档（判断过程留痕）、一份处理后的上报版、一张处理清单。上报版交出去，另外两样留在手里——以后有人问"这个星号是谁"，翻清单就有答案，不用再翻两万字的原稿。

三个实战细节。其一，表格里的敏感信息别漏。补贴表才是重灾区，我的补充指令是让智能体用表格工具（header_read、column_read 这类切片读取）把表格内容也扫一遍，而不是只读正文段落。其二，复核要看上下文：同一个手机号，在"联系人"栏是保留项，在花名册里可能是敏感项，机器分不出业务含义，只能按位置全标，取舍在人。其三，全程不出域：这套流程跑在察元的本机 MCP 服务上，只监听 127.0.0.1，模型走内网端点。个人信息保护这件事，工具链自己得先干净——把带身份证号的文档贴到某个在线工具里"检测敏感信息"，等于把问题复制了一份传出去。

那次实战的结果：机器标了几十处，人工复核剔掉几处误报，也补上一处漏网的——号码中间加了空格，模式没匹配上。初筛覆盖了绝大部分工作量，剩下那一成还是靠人的眼睛，这也正是我对这类工具的定位：批量干粗活，边界判断留给人。敏感信息识别是概率活，漏报误报都正常，正式上报前的人工逐页复核一步不能省，机器结论仅作辅助参考。

给同岗位朋友的一句话：批注定位的价值不在"找得全"，在"找得可追溯"。每一处疑似都有批注、有结论、有留痕，出了问题翻批注就行——这比一个"检查完毕，未发现问题"的弹窗让人踏实得多。
