# 助手进化与回滚：版本快照的治理思路

AI 幻觉治理聊了一整年，多数讨论停在模型层。但实际用下来，真正高频翻车的不是模型，是提示词——我改了一版校对助手的系统提示，误报率悄悄翻倍；同事"优化"了术语统一助手的模板，第二天全组的批注风格全变了。提示词就是没有版本号的代码，没有治理就是裸奔。

围绕察元AI文档助手的助手体系，我把团队里被问最多的几个问题整理成一篇问答，讲讲助手进化的治理思路。

## 问：助手为什么需要版本快照？

因为助手会变，而且变得比想象中频繁。系统提示、用户模板、输出格式，任何一个字段调整都相当于发了一个新版本。察元的 README 里提到了版本快照、评估、晋升、回滚、影子双跑这些设计方向，属于产品规划沉淀的能力思路，不是已经上线的具体按钮。核心想法很朴素：每次改动留档，出问题能退回上一版。这个思路和代码世界的 Git 没有本质区别，只是对象从代码换成了提示词。

## 问：评估和晋升指什么？

评估是拿固定的样例集去跑候选版本，看输出质量是否达标；晋升是候选版本通过评估后转为正式版本。换句话说，改动不直接生效，先过考试再上岗。在应用层，这套流程完全可以用笨办法模拟出来，成本不高，后面细说。

## 问：这些能力现在能用吗？

如实说：README 提及的是设计取向，别当成已有功能去点按钮。但当下的工具已经够搭一套"手工版治理"：用 `assistants_get` 导出助手定义和提示词，落成文件存进 Git，这就是你的版本快照；每次改提示词前先提交一次，改完跑固定样例对比输出，这就是评估；效果退化就回滚到上一个提交，这就是回滚。配合察元 AI 编审里的模板与规则功能——aidooo 扩展名文件导入导出、规则制作与交换——团队之间还能把治理好的规则正式交换，而不是靠聊天软件传截图。

## 问：回归样例集怎么建？

从历史误报里挑，这是最真实的语料。比如序号体例检查这条：

```
检查标题/条款序号（一、（一）、1.）是否层级混乱，批注指出
```

拿它跑十段曾经出过问题的文本，新旧两版提示词各跑一遍，对比问题列表的差异。十条样例就能拦住大部分退化，投入产出比非常高。

## 问：快照里应该存什么？

按自定义助手的定义结构存全：系统提示、用户模板、模型类型、输入来源、输出格式、写回动作、显示位置，一个字段都别省。我吃过亏——只存了提示词正文，两个月后要回滚时发现忘了它当时挂在哪个菜单、写回动作用的是批注还是替换，复原花了半小时。快照的意义在于"回到当时"，缺一个字段就不是当时。团队协作时，这份完整定义还能直接给同事导入，比口头传话靠谱。

## 问：不想从零自建助手呢？

用 `assistants_search`，能检索数千个察元助手；`assistants_list_domains` 离线就能看领域目录，不配模型也能先逛。别人的成熟助手拿过来当基线，比自己从零写靠谱得多；用 `assistants_get` 拿到定义之后，照样纳入你自己的版本管理流程，治理习惯不断档。

## 问：助手数量多了怎么管？

先分域再看数。`assistants_list_domains` 能离线列出领域目录，把治理粒度定在领域级：每个领域指定一个负责人、一套样例集，快照按领域归档。数量上来之后检索比翻目录快，`assistants_search` 按需检索配合领域分区，几十个助手也能维持住秩序，不至于长成一团乱麻。

## 问：治理做到什么程度算够？

我的标准是两条：一，任何一个助手当前生效的提示词，都能在十分钟内找到对应文件；二，任何一次改动，都能说清楚改了什么、为什么改、谁批的。做到这两条，规模再涨也不会乱。

## 边界与心得

治理思路说到底是工程纪律，助手数量越多越值钱。我的建议是趁助手还只有十几个的时候，把导出存档的习惯养起来；等规模上去了再补流程，成本会高一个量级。辅助工具进化得再快，也不该成为放弃管理的借口——恰恰相反，进化越快，快照和回滚越值钱。
