# 密级标识查漏：辅助不定密，但能先替你筛一遍

后台常有同行留言问密级标识的事，攒了几条有共性的，这次一次说清。先亮观点：定密是法定程序，AI 干不了也不能干；但定密之前把密级标识的疑点筛出来，机器干得又快又稳。我用的工具是察元AI文档助手（WPS 加载项加本机 MCP 服务，开源），下面按问答展开。

**问一：密级标识最容易错在哪？**

我见过的退回件里三类最多。一是该标没标——涉密文稿生成时套了普通模板，版头密级位置是空的；二是标错了位置——密级标识该在版头醒目处，有的稿件把它写进了文末说明；三是密级和保密期限的写法不规范。还有衍生问题：一份文件定了密，从它摘编的材料忘了同步标识，摘编稿裸奔外发，这类最危险，因为经手人自己都忘了源头是涉密的。

**问二：AI 能帮忙定密吗？**

不能，我也不建议任何人这么用。定密有法定程序、有定密责任人，这个环节没有机器的位置。AI 能做的是前置筛查：察元里"保密检查"助手会检查密级标识情况，配合"涉密关键词提取"助手，把疑似涉密表述、涉军涉装内容、项目编号这类线索找出来，给出分级风险提示，供定密流程参考。辅助参考，不替代定密程序和人工保密审查——这句是使用红线，谁用都得先立这个规矩。

**问三：具体怎么操作？**

我固定两条。第一条用在核稿时，让 AI 把线索全亮出来：

```
提取这份文档中的疑似涉密关键词和敏感表述，按类别汇总，并检查有无密级标识
```

第二条用在批注定位，问题要落到段落上才好改：

```
对上一步发现的疑似涉密表述逐条添加批注，注明风险类别，不要修改正文
```

察元的写回机制有确认门槛：智能体加批注必须明确确认才会写入，AI 不能悄悄改稿。对涉密文书场景这一点很关键——机器只建议，动笔的权力永远在人手里。

**问四：误报漏报怎么办？**

都有。正常的业务编号偶尔被认成疑似涉密编号，属于误报，人工排除就好；漏报更值得警惕，变形写法、行业内的代称，机器未必认得。上个月碰到个例子：文稿里出现一个设备代号，机器标了疑似涉军涉装，拿去一问，确实是内部叫法，外发版本换成了公开名称——这串代号看着就像普通型号，人眼十有八九会漏。所以我的定位是"多一道筛"，不是"换一道闸"。AI 筛一遍五分钟，人工复核再过一遍，两道筛总比一道强，但最后一道永远是人。

**问五：材料安全吗？**

这是问得最多的。察元的模型端点支持内网部署，Ollama、LM Studio、Xinference 这些 OpenAI 兼容端点都能接；MCP 服务只监听本机回环地址，检查过程文档不出这台机器。涉密敏感内容的稿件，这个前提是底线。都说政务大模型落地难，我看很多单位落不了地的第一原因，就是数据出域这关过不去——先把环境做对，再谈用得好不好。

**问六：多久跑一次？**

三个节点：拟稿完成自查一次，核稿时一次，外发或归档前一次。前两次是给作者和核稿人省眼睛，第三次是兜底。有人担心反复跑会乱改稿子——不会，察元的校对默认 dryRun，只返回问题清单不碰正文，确认之后才落成批注，检查这个动作本身没有副作用，多跑不亏。

**问七：和我们现有的保密审查流程冲突吗？**

不冲突，位置在前头。机器筛查放在拟稿人自检环节，人工保密审查照走不误，该谁签字谁签字。机器筛出的疑点清单反而能让保密审查聚焦——审查人员拿到的是一份标了位置的线索表，而不是从零开始翻全文。

一句话收束：密级标识查漏这件事，机器当筛子，人当闸门，制度当堤坝。筛子越密越好，闸门永远别交给机器，这是我用了一年之后越来越确定的事。
