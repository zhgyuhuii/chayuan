# 敏感段本地、公开段云端：分流策略与责任边界

数据安全不出域喊了两年，落到文档场景其实很拧巴：全走本地，好的云端模型用不上，效果和成本都吃亏；全走云端，红线又摆在那里。我们单位实践下来的答案不是二选一，而是分流——敏感段落走本地模型，公开内容走云端，中间用工具把边界切干净。用察元AI文档助手讲讲完整做法，它的设计取向是离线内网优先，同时也支持并行配置云端供应商，正好够搭这套方案。

## 第零步：先把"敏感"识别出来

分流的前提是识别，识别不清就分流不动。察元内置的保密检查助手会从密级标识、涉军涉装、单位身份、联系方式、项目编号、商业秘密分级等维度给风险提示；另一条提示词用来抓硬识别项：

```
查找疑似身份证号、手机号、银行卡号并批注
```

这两道跑完，文档的敏感点就基本标出来了。编审类里还有个涉密关键词提取，把文稿里的涉密要素先拎出来，和保密检查配合用，识别这一步能做得更扎实。强调一句：这些输出都是分流依据，不是定密结论，两者性质完全不同。

## 第一步：本地模型兜住敏感段

在察元里配置 Ollama 等 OpenAI 兼容端点作为本地渠道，敏感段落涉及的校对、改写只在本地模型上发生，数据不出本机。操作上利用输入来源设置：把处理敏感内容的自定义助手设为仅选区，选中那段再跑，路径清晰可控，不会误把整篇带出去。

## 第二步：公开内容走云端

察元支持并行配置云端供应商，OpenAI、DeepSeek、阿里百炼、千帆、Gemini 都行。公开章节的润色、扩写、翻译交给云端，效果好速度快。按 Token 计费之后，分流同时也是成本优化——贵的模型只花在值得的段落上，账单立刻好看很多。

## 第三步：外发前的脱密关口

要拿去外部协作的文档，走察元的脱密工具链：先调 `declassify_status` 看脱密模块状态；`declassify_preview` 只预览不写盘，看清楚会替换哪些内容；`declassify_apply` 需要 confirm 加 password 加 keywords 三要素才真正执行；执行后觉得不对，还有 `declassify_restore` 可以恢复。这套设计把脱密做成了显式、可逆、有门槛的操作，比手工查找替换可靠一个量级，也留下完整的操作痕迹。

## 跨文档场景的分流

整套方案里最容易被漏掉的是多文档交叉核对——两份文稿要核对术语和数字是否一致，其中一份带着敏感段。这时别整份丢出去，先用敏感信息提示词各自扫一遍，涉敏感的那份锁定在本地渠道处理，公开部分再做交叉核对：

```
打开目录下这几份文档，交叉检查错别字与术语是否一致
```

分流规则跟着文档走、不跟着任务走，这条原则立住了，跨文档协作才不破功。

## 责任边界：工具不背书，人来签字

必须说清楚：以上全部是辅助参考，不替代人工定密和法务审核。保密检查助手给的是风险提示，脱密工具执行的是你给它的规则，分流的正确性取决于你的分级判断。我们单位的规矩是 AI 标注加人工复核双签，任何一份外发文档的定密责任都在人，这句话白纸黑字写进了操作规程。还有一件审计时绕不开的事：云端渠道的日志与留存政策要提前纳入评估，把"内容去了哪、留了多久"写成文档，被问到的时候拿得出手。

## 一张执行清单

- 文档进来：保密检查助手加敏感信息提示词，先标出敏感点
- 日常编修：敏感段设仅选区走本地，公开段落走云端
- 对外发出：declassify_preview 预览，确认后带密码执行，留档备查
- 每月抽查：复核分流是否有漏网，规则是否要更新

分流的本质不是技术方案，是责任方案：把每一段内容的去向说得清楚，红线和效率就能同时保住。工具把边界画好了，剩下的判断和签字，仍然是你我的事。
