# 选区还是全文：输入来源的选择策略

按 Token 计费用了一个月，我们组最大的心得就一句话：账单不是模型挑出来的，是"全文"两个字喂出来的。一份三十多页的汇编材料，明明只有第三章的政策口径可能有问题，同事顺手点了全文检查，跑完一看，九成的 Token 花在根本没问题的段落上。这不是模型不行，是输入策略没选对。

用察元AI文档助手做校对和编审，这个问题绕不开。它以加载项形式运行在 WPS 文字里，配置自定义智能助手时，"输入来源"就三个选项：优先选区、仅选区、全文。选项不多，但值得认真讲讲——这是成本、精度、速度三个变量的交汇点，选错一个，另外两个都跟着遭殃。

## 三种模式，三种打法

**全文：终检专用。** 整份文档都要过一遍的场景才值得开全文，典型如发文前的最后一道检查。好处是覆盖完整、不留死角；代价是长文档既慢又贵，而且问题列表容易被琐碎问题淹没，真正要紧的那两条反而被冲淡。

**仅选区：精确打击。** 你明确知道问题在哪一节、哪张表的时候，选中那段再跑，模型只看这一段。改一段审一段的交互式编修，这是最省的模式，也最能保持注意力聚焦。

**优先选区：日常默认。** 从命名看就是折中方案：有选区先处理选区，没有选区再看全文。日常随手用、懒得纠结的时候选它，多数情况下不会错得太离谱。

## 长文档：先看元数据，再决定怎么喂

全文模式最大的坑是长文。察元的 MCP 工具里有一个 `document_meta`，先问它：文档名称、字数、段数，以及是否建议分块。经验法则是：`document_get_text` 超过约 80k 就需要 force:true 强取，或者干脆改用 `document_chunks` 按 cursor/limit 分页分块喂给模型。

分块不只是规避限制，更是省钱的姿势——问题密度高的章节先跑，纯数据附录根本不用进模型。配套的提示词可以直接抄：

```
帮我检查文档中的错别字，用批注标出原文和建议改法
```

如果只锁定表格区域，要求可以更具体：

```
重点检查表格单元格里的错别字，批注必须钉在具体错字上
```

## 一张速查清单

- 一万字以内的发文终检：全文，一次跑完不留死角
- 只改某一节、某张表：仅选区，选中再跑
- 日常随手校对：优先选区，不用想
- 超长汇编：先 `document_meta` 看分块建议，再 `document_chunks` 逐块处理
- 多文档交叉核对：交给外部智能体经 MCP 编排，逐份处理更稳

## 输入选好了，输出也别浪费

输入来源决定喂什么，写回动作决定模型往哪儿放结果，两头要配套着选。察元的写回方式有八种：插入到光标处、插入到每段后面、插入到文档最前面、替换、添加批注、链接形式批注、批注加替换、追加到文末，外加仅生成结果。我的搭配经验是：仅选区模式配"仅生成结果"，看完即弃，适合临时确认某个疑点；全文终检配"添加批注"，问题钉在原文位置，逐条核对方便；真正有把握的机械修正才敢用"替换"，而且先看预览再确认。

还有一个容易被忽略的细节：选中内容跑完之后，如果要把结论落到文档的其他位置，定位别靠口头描述去猜。`document_locate` 会返回多个候选锚点，让智能体先确认位置再写回，比"大概在那一段"可靠得多；锚点对不上宁可重找，别硬写。

顺便说一句，如果不想自己配置，察元自带 29 个内置助手，拼写与语法检查、术语统一、检查段落序号格式这些都是现成的，开箱即用；自定义助手适合你有了固定私有打法之后再建，把系统提示、模板、输入来源一起固化下来。

## 边界与心得

输入来源解决的是"喂什么"，不解决"信什么"。全文跑完不代表没问题，仅选区跑完更不代表其他段落干净——它是成本工具，不是责任工具。真正发文前的人工把关流程，一步都不能省，这一点怎么强调都不过分。

我的习惯现在固定成两步：日常交互用优先选区，控制单次成本；发文前用全文加终检提示词跑最后一遍，买一个覆盖完整。账单降下来是一方面，更重要的是问题列表变短了，人反而看得更认真。工具的价值不在跑得多，在于每一次跑都值得看。
