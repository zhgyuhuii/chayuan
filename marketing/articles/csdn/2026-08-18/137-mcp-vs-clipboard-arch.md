# 复制粘贴架构的终结：MCP 时代的文档交互

MCP 协议生态今年彻底爆发，Claude Code、Codex CLI、Cursor Agent 一水儿地往工具生态上接。但有个现象很有意思：很多人口口声声用 AI 办公，实际流程还是老四样——复制一段文档、切到 AI 窗口、粘贴、拿到回答再复制回来。模型在以月为单位进化，交互却停在剪贴板时代。这一年我把文档处理全面迁到察元AI文档助手的 MCP 链路上，越用越确信一件事：以复制粘贴为骨干的"AI 文档协作架构"，正在被终结。不是被更好的模型终结的，是被更好的接口终结的。

## 旧架构的三个死穴

第一，上下文丢失。你粘给 AI 的永远是一个片段，它不知道这份文档的标题层级，不知道表格里那一列的统计口径，建议自然隔靴搔痒。第二，位置丢失。AI 告诉你"第三段那个词用错了"，你还得自己回文档里找第三段；表格、题注、序号这类结构性内容，粘贴出来再搬回去，格式十有八九要乱一遍。第三，不可批量。一百处错别字就是一百次来回，号称自动化的人机协作，退化成人肉搬运。这三个死穴是结构性的，模型再强也补不上，因为问题出在通道上，不出在脑子上。

## MCP 架构换的是地基

察元的做法是把本机 MCP 服务作为文档与智能体之间的直连通道，AI 不再接收粘贴的片段，而是直接操作文档对象：document_list_paragraphs 拿到带锚点的段落列表，document_locate 按内容定位并返回命中锚点，长文交给 document_chunks 分块读取；写回侧，document_add_comment 能把批注钉在具体的字上，document_apply_ops 一次最多执行 200 个写回操作。锚点是这套架构的关键发明——AI 明确知道自己在读哪一段、要改哪一句，误伤率比"贴回去"低一个量级。除了工具调用，这套服务还提供几个只读资源，健康状态、助手清单随时可取，调试和巡检都用得上。Claude Code 用户一行命令接入：

```bash
claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62588/mcp
```

## 一个最能说明问题的例子：表格插行

老流程大家都熟：把表格导出来、在别处插行、粘回去、调格式、祈祷别错位。新流程一句话：

```
在"合计"行上面插入一行，列结构和上一行一致
```

AI 会先用 header_read、column_read 这类表格工具读表头和列结构，找到"合计"行的锚点位置，然后按显式坐标执行插入。注意这个细节：AI 负责找锚点，工具只按明确坐标执行，不靠猜。这正是 MCP 架构和剪贴板架构的本质区别——操作是结构化的、坐标是显式的、结果可校验的，而不是靠人在两个窗口之间当搬运工和校对员。

## 迁移清单：从剪贴板搬到 MCP，做对三件事

第一件，注册。Claude Code 用上面的命令行；Cursor 在项目里建配置文件；Codex 在它的配置里加一段服务地址。各家写法不同，但都是一次性的活。第二件，验证。注册完先打健康检查，确认服务在线再开工，别把配置错误的锅甩给架构。第三件，改造提示词。剪贴板时代的提示词都是"帮我看这段话"，迁移之后要改成"检查这份文档"——让 Agent 去调工具读全文、拿锚点、落批注，而不是继续伺候你贴进来的片段。第三件最容易漏：很多人接好了 MCP，提示词还是老一套，等于新车挂着一挡上高速，怪车没劲。

## "终结"这个说法是不是太满

说清楚一点：被终结的不是复制粘贴这个操作本身，贴段参考资料当然还要复制。被终结的是"AI 与文档的协作以剪贴板为骨干"这个架构。而且直写文档的能力越强，安全带就要越紧：document_replace 不确认就只给 preview，写批注、批量写回都必须显式 confirmed:true，写操作的默认姿态是"先给人看"。通道升级的同时把确认机制升级，这才算负责任的直连，否则只是把鲁莽的搬运换成了鲁莽的直写。还有一点常被忽略：直连架构下，批量操作的杀伤力也被放大了，批量写回一次最多 200 个操作，若无确认直写，出错就是批量出错。确认机制不是产品保守，是直写能力的配套件。

适合谁：天天和长文档、多文档打交道的编辑、秘书、法务、科研人员，迁移收益最大；偶尔在聊天框问两句的轻度用户，剪贴板暂时还够用，不勉强。

能力上来了，交互就该跟着换代——让 AI 对着你的文档干活，而不是隔着一层玻璃听你复述。
