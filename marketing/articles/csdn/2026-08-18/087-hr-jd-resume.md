# HR 的 JD 与简历整理：表单提取换个用法

在 HR 朋友的工位边看她筛了一下午简历之后，我确信一件事：HR 是被 AI 落地浪潮遗忘得最严重的岗位之一。不是没有工具，是卖概念的多、能嵌进日常文档流程的少。聊完之后，我把她工作流里能自动化的部分整理成四条清单，工具用察元AI文档助手——WPS 加载项形态开箱即用；Claude Code、Cursor 这类 Agent 也能通过 MCP 协议直连它的四十六个文档工具，这也是 MCP 生态爆发给办公场景带来的新可能。

## 用法一：JD 写作的三个助手接力

招聘 JD 看似短，实则反复改。她现在的流程是三步：草稿写完用"润色优化"顺掉语病；用"正式化改写"把口语腔收紧，比如"我们想要一个能扛事的"改写成清晰的职责表述；最后用"生成摘要"压出一段三行岗位速览放 JD 顶部，候选人十秒内知道这岗干什么。三个都是内置助手，选中文字一键跑，改写结果可选只生成不落盘，先比后用。

## 用法二：简历字段抽取，表单提取换个用法

这是本篇的重点。察元有个"表单智能提取"助手，设计用途是合同、公文抽字段输出 JSON。简历本质上也是一张非结构化表单，直接套用：

```
从选中的简历中提取字段输出JSON：姓名、学历、毕业院校、工作年限、最近两段任职的公司与职位、技能关键词；只提取原文明确出现的信息，缺失字段填null，不要推断
```

"不要推断"这句是重点。简历初筛最忌讳 AI 脑补——候选人写"熟悉"，抽取成"精通"，一字之差筛错人；缺失字段填空而不是编一个，是这类工具能不能用的底线。抽取结果粘进 WPS 表格做横向比对，五十份简历的结构化台账半小时能出来，短名单会上直接用。

## 用法三：敏感信息预检

简历含身份证号、手机号、家庭住址，流转给用人部门前要脱敏。用这条：

```
查找疑似身份证号、手机号、银行卡号并批注
```

批注定位到具体位置，人工确认后再处理。察元另有脱密预览能力，只提示不写盘，确认之后才真正动手，给个人信息内部流转留了一道闸。做 HR 的都知道，个人信息泄露这类事故，出一次就够喝一壶。

## 用法四：面试跟进清单的结构化

攒了三年的面试反馈和会议纪要，用"提取行动项"的思路反向操作——把"待跟进候选人"从散落文档里抽出来，注明岗位、当前状态、下次联系时间。HR 的跟进断档，多半不是懒，是信息散；候选人等两周没消息就去了别家，损失的是招聘周期。面试官口头反馈整理成的记录，用"生成会议纪要"助手压成标准格式存档，背调和复盘时都有据可查。JD 定稿前再用"提炼关键词"抽一遍岗位核心词，和发布平台的检索词对齐，曝光量是靠这些词吃饭的。

## 边界说明

- 初筛是分流，不是决策。AI 抽字段的价值是把明显不符的快速归档，进入短名单的每一份简历，仍然要人读全文。
- 简历是候选人的个人信息，本地处理优先。察元支持 Ollama 等本地模型端点，招聘数据可以不出公司网络。
- 批量场景适合 MCP 直连：招聘季几百份文档，让 Agent 循环处理，写回操作默认预览模式，人工确认后才落盘。

这套清单适合谁：招聘 HR、猎头助理、管校招的行政、兼职做雇主品牌的内容岗。门槛方面，HR 不需要懂什么 MCP 协议——WPS 里点开加载项就能用；真要批量处理，拉个会配置的同事用 Claude Code 挂上服务即可，地址就是本机回环加端口那一条，一次配好长期有效。

HR 这个岗位这两年被"AI 招聘"的概念轰炸过很多轮，真落地反而朴素：字段抽取加敏感信息预检这两个点，就够把一个下午的重复劳动缩到一小时。岗位不会被工具替代，但会用工具的 HR，会先一步从重复劳动里走出来，去做人做得了、机器做不了的事——比如判断一个人和团队的匹配度。
