# 一、（一）、1. 层级乱成一团：段落序号检查一键体例

上个月我们的半年情况报告被上级退回，理由就一行：层次序号混乱，请校后重报。打开一看我自己都脸红：第二部分从"一、"直接跳到"1."，中间的"（一）"没了；第三部分的"(一)"用了半角括号，和前面的全角"（一）"长得不一样；还有一处"1、"，顿号句号混着来。一份两万字的报告，五种序号写法，领导批注四个字：体例太乱。

复盘下来，乱源有三个。一是拼稿：报告是五个科室的材料拼的，各家有各家的层级习惯，粘进来就是"联合国"。二是改稿：删掉一层内容后序号没有重排，"（三）"后面直接接"（五）"。三是肉眼：改到第七稿，谁也没力气从头数序号。人工理不顺的事，正好是机器的强项——序号检查本质是按段落逐个核对模式，不费脑子，但费眼睛，而费眼睛的活就该交给 AI。

察元AI文档助手里有个内置助手叫"检查段落序号格式"，WPS 里选中全文一键跑。我后来又配了条提示词，给连 MCP 的智能体用，查得更细：

```
检查标题/条款序号（一、（一）、1.）是否层级混乱，批注指出
```

跑完它把问题列得明明白白：哪一段跳级、哪一段括号是半角、哪一处顿号该是下脚点，每条都以批注形式钉在对应段落上，拟稿人按批注一条条改，改一条消一条。

进阶玩法是让外部智能体通过 MCP 干这活。察元的本机 MCP 服务有 46 个文档工具，其中 document_list_paragraphs 能把全文段落连同锚点列出来，AI 逐段核对序号模式，发现问题再用 document_apply_ops 一次把几十条批注批量写回——单次最多 200 个操作，两万字报告的序号批注一轮跑完。整个过程文档都在本机，模型走内网部署的 DeepSeek 或 Qwen，一个字不出域。今年大家都在讲 AI Agent 办公落地，落在我桌上不是替我写材料，是替我数序号。

三个实操细节说给同路人。第一，先约定层级规范再跑检查：我们单位的体例是"一、（一）、1.（1）"四层，往下用"①"，提示词里写清楚，AI 按你的规矩查，不是按它想象的规矩查。第二，让 AI 只做批注、不直接替换。序号牵一发动全身，自动重排容易把本来不错的层级也动了，人过一眼再改最稳当。第三，长文档跑检查时工具会提示建议分块，跟着走就行，不影响批注落点。

顺带说个新情况：现在不少初稿是 AI 起草的，这类稿子的序号尤其爱飘——模型写长文时层级会越走越乱，"（三）"写着写着变回"1."，人抄改时还顺手把错误继承下来。加载项里有个"AI 痕迹检查"助手（保守评估），序号体例混乱有时正是痕迹之一。所以在单位里我把序号检查放在两个节点：拼稿后一次、AI 初稿到手后一次，都是体例最容易散的时候。

另一个提效做法是把这条检查做成按钮。察元支持自定义智能助手：系统提示、输入来源、写回动作、显示位置都能配，我把序号检查的提示词固化成一个右键菜单项，核稿时选中全文点一下就出结果，不用每次重新打字。科室里最高频的检查，都值得花两分钟做成按钮，用的人多了体例就统一了。

现在的流程定型为两跑：拼稿当天跑一次序号检查，把五个科室的层级先统一；终稿上报前再跑一次，专抓改稿改出来的断号。上次的月度报告，三分钟出结果，两处跳级、一处半角括号，改完直接报，再没收到过"校后重报"。

说句边界话：序号检查管的是体例统一，不管内容对错，层级理顺了不代表逻辑顺了——先想清楚层次，再让机器对齐格式，顺序别反。工具是开源的（Apache-2.0，当前版本 4.1.2），模型可配内网端点。把数序号这种活交出去之后，人才能腾出眼睛看真正要紧的东西。
