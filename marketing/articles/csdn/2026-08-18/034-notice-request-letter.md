# 通知、请示、函：三类常用文种的 AI 审查要点

在机关写材料，一年到头数下来，写得最多的就是通知、请示、函三个文种。文种不同，出错的点也不同：通知容易散，请示容易越界，函容易串味。这一年我把察元AI文档助手当审稿人用，慢慢攒出三类文种各自的审查要点，整理成这篇给同岗位的朋友参考。先说明，这是 WPS 里就能用的开源加载项（Apache-2.0，当前版本 4.1.2），配内网模型端点也能跑，政务大模型落地这个话题，落到文秘手上就是这些具体活。

先说通知。最容易出问题的是四处。一是标题文种与内容不匹配，明明是布置工作，写成了"意见"；二是转发性通知层层转发，标题转了三层比正文还长，该简化没简化；三是附件说明与附件实际名称不一致——正文写"附件：实施方案"，附件封面却是"实施细则"，这种错单看一份永远发现不了，多文档交叉检查正是 AI 的强项：

```
打开目录下这几份文档，交叉检查错别字与术语是否一致，重点核对正文附件说明与附件标题是否对得上
```

四是执行要求模糊，"尽快落实"到底多快、报材料到哪天截止，AI 能把这类缺时限、缺责任主体的段落圈出来提醒你。

再说请示。请示的规矩多，机器能盯的是这几个点：一文一事——两件事写成一份请示，AI 读到主题切换可以提醒；主送机关只能有一个，多余的它会圈；文种别混用，"请示报告"这种合成文种名会被抓出来；结语是不是"妥否，请批示"一类规范表述，写成"特此报告"就串味了；还有签发人——上行文的标配，最常漏。我核稿时习惯丢一句：

```
这是一份请示：检查是否一文一事、主送机关是否唯一、结语是否规范、有无签发人标识，问题用批注标出
```

这几个点里，标题和附件是硬伤，执行要求是软肋——从退回件的统计看，软肋比硬伤多，因为硬伤打印出来就能看见，"尽快落实"这种模糊表述藏在通顺的句子里，读三遍都不觉得有问题。

第三说函。函是平行文，商洽工作、询问答复都用它，最容易犯的毛病是"口气错位"——写成上对下的命令口吻，或者下对上的请示口吻。这对 AI 反倒是舒服活，语气风格正是语言模型敏感的地方。加载项里"正式化改写""政策/公文风格改写"两个助手可以改写指定范围（优先选区、仅选区、全文都行），把口气不对的段落圈出来单改；复函记得核对有没有引对方来函的标题和文号，这个点我写进提示词让它顺带查。再配合"术语统一"助手，把"贵单位/你单位"这类称谓前后不一的地方捋齐。

操作层面补两个细节。一是查错别字的基线动作，三类文种通用：

```
帮我检查文档中的错别字，用批注标出原文和建议改法
```

批注钉在原字上，拟稿人看得见原文和建议改法的对照，改不改、怎么改由人定。二是提法一致：通知类文稿里"专项工作"写着写着变"专项整治"，"各单位"变"各有关单位"，术语统一助手能把这类漂移找齐——提法一致在公文里不是小事，口径散了比错别字更扎眼。

还有个常被问的问题：WPS 里的内置助手和外接 MCP 智能体怎么选？我的经验是日常核稿用内置助手，点开就用，快；需要跨文档、跨步骤的复杂检查——比如正文与附件交叉核对——才动用智能体，让它在几份文档之间来回读。工具形态不重要，重要的是检查项一项不落。

三个文种共同的底线检查，是发出前的终检，我固定用一条提示词兜底：

```
帮我做发布前终检：错别字、标点、数字前后一致性、表格与正文是否一致；全部用批注输出；最后给我一份问题分级摘要（严重/一般/建议）
```

文种判断本身建议留给人。AI 分得清大部分文种特征，但边界场景它会犹豫：既有商洽又有请求事项的复合件，到底用函还是请示，最终得听业务口径和领导意见。工具这边全程可以跑在本机（MCP 服务只监听 127.0.0.1，模型接内网 Ollama、Xinference 都行），材料不出机器，这是敢拿内部文稿喂它的前提。三个文种，十来条要点，机器守细节、人守口径，一年能省下不少核稿的深夜——这就是我理解的、把 AI 用在最该用的地方。
