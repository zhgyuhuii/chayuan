# 端口 62588 被占了怎么办：CHAYUAN_MCP_PORT 改端口实录

本地部署爱好者的宿命：服务越装越多，端口早晚打架。我机器上常年跑着 Ollama、LM Studio，还有察元桌面版知识库跑在 62581，一直相安无事。直到上周一早上，Claude Code 里察元的 46 个工具集体消失，一段排错实录就此展开，顺手把处理过程完整记下来，给同病相怜的人省点时间。

## 现场：像是服务挂了，其实不是

现象很典型：Claude Code 提示 MCP 服务连不上，工具全部不可用。按老规矩先打健康检查：

```bash
curl http://127.0.0.1:62588/healthz
```

不返回 online。第一反应是服务没起来，重启 WPS——没用。加载项明明装得好好的，昨天还正常用着。这时候冷静下来想：healthz 不通只有两种可能，要么服务没起来，要么服务起来了但我够不着它。第二种可能的头号嫌疑犯：默认端口 62588 被别的进程抢走了。

## 定位：一条 netstat 定案

Windows 下一行命令查端口占用：

```bash
netstat -ano | findstr 62588
```

输出显示 62588 已经被另一个进程监听——上周装的一个本地小工具，默认也用这个段位的端口，撞了个正着。察元的 MCP 服务默认端口就是 62588，端口被占，服务自然起不来。病因找到，剩下的就是换端口，而且不用改任何代码。回头看这次排错，healthz 加 netstat 两条命令就完成了定位，前后不到五分钟；如果没有先分诊的习惯，大概率会走上重装加载项、重装智能体、清配置的弯路，折腾一小时还未必能好。工具越智能，越要给排错留一套笨办法：先确认事实，再动手改。

## 为什么偏偏是端口

察元的 MCP 服务是一个单文件常驻进程，Windows 上注册开机自启，不依赖 Node.js 环境；加载项、sidecar、智能体三方都靠 62588 这个地址会合。这类本机服务架构的代价就是端口独占：地址一旦被抢，整条链路一起断。而这几年本地部署爆发式增长，一台机器上挤着 Ollama、LM Studio、各种 sidecar，默认端口撞车几乎是必然会遇到的事，遇到不丢人，会处理就行。

## 处理：CHAYUAN_MCP_PORT 三步闭环

察元支持用 CHAYUAN_MCP_PORT 环境变量指定服务端口，整个处理就三步。

第一步，把新端口写进用户环境变量：

```bash
setx CHAYUAN_MCP_PORT 62599
```

第二步，让服务读到新值。setx 只对之后启动的进程生效，注销重登，或者重启 chayuan-mcp 进程，让自启服务用新端口拉起来。macOS 和 Linux 用户思路完全一致：把 CHAYUAN_MCP_PORT 写进对应平台的服务环境里，重启生效，差别只在写法。

第三步，验证。对着新端口再打一次 healthz：

```bash
curl http://127.0.0.1:62599/healthz
```

返回 online，服务侧收工。

## 最容易漏的一步：同步所有客户端

服务搬家了，客户端还指着旧地址。Claude Code 用新 URL 重新注册：

```bash
claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62599/mcp
```

Codex 的 config.toml、Cursor 的 .mcp.json 里那个 url 字段也要同步改，不然就是"服务明明在线、Agent 就是连不上"的灵异现场——其实不是灵异，是地址没跟上。改完把每个客户端的会话都重开一遍，工具列表全部拉得出来，才算闭环完成。我就是漏了 Cursor 那份配置，多排查了二十分钟，教训深刻。

## 复盘三条

一，排错顺序别乱：先 healthz 分清"服务问题还是链路问题"，再 netstat 查占用，直奔病因，别上来就重装。二，本地服务多的机器，装新工具前先扫一眼常用端口，62581、62588 这些常驻端口心里要有数，与其事后救火，不如装机时错开。三，改端口是"环境变量、重启服务、同步客户端配置"三步闭环，少任何一步，它都会在半小时后以另一种报错回来找你。四，改完做一次全链路验收：healthz、工具列表、实际写一条测试批注，三层全过再交还使用，别只验到一半就宣布修复。

## 边界收尾

换了端口，安全模型没有变：服务依然只监听 127.0.0.1，本机即信任边界，不需要配置 Token。真有跨机器访问的需求，正路是走代理方案，而不是把监听地址裸露到网络里。这套流程也适合所有本地服务多的开发者和运维：不止察元，任何依赖默认端口的本机服务被占，方法论完全一致。

端口冲突是小事，但排错的章法是通用能力——下次任何本机服务"莫名失踪"，healthz 加 netstat 这套组合拳照打不误。
