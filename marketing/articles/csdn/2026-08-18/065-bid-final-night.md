# 开标前夜终检：表格与正文数字一致再睡觉

先讲那个让我后怕的事。去年一个项目周四开标，周三夜里十一点四十，我在打印店等封标前的最后一遍通读，商务同事突然捅我：正文商务响应里写的是"报价包含五年运维服务"，报价表里运维费只列了三年。就差这一行。要是当时没翻到那一页，第二天连补救的余地都没有——报价以开标一览表为准，正文口径自相矛盾，轻则现场澄清质询，重则按无效报价处理，全看评委较不较真。

那晚之后，我把开标前夜的终检流程整个重做了一遍。复盘下来是三个坑，一个一个说。写给出标书岗的同事：这三条都是拿心跳换来的。

## 坑一：表格里的错字肉眼扫不出来

报价表单元格窄、字号小，夜里十一点以后，眼睛会自动跳格子，这是生理规律，不怪人。后来这类活交给 WPS 里的察元AI文档助手做校对，提示词专门强调钉在错字上：

```
重点检查表格单元格里的错别字，批注必须钉在具体错字上
```

批注直接落在出错的单元格里，第二天早上按批注逐条清，不会漏，也不用再通读一遍受二茬罪。

## 坑二：数字勾稽只对了合计，没对口径词

我们的老流程是"合计对上就睡觉"，但那晚的事故恰恰不在合计，在口径词——年限、周期、包含范围这类词和数字的组合。现在的勾稽是两条提示词一起跑：

```
核对数表与正文数字是否一致（合计、百分比）
```

```
检查正文里"X年""X个月""含/不含"这类年限周期和包含范围的表述，与报价表逐项对照，不一致的批注标出
```

第二条是我们自己加的，专治那晚那种坑。数字一致不等于口径一致，"三年"和"36 个月"数字上能对上，商务上是两回事。报价表的大写金额也在勾稽范围里——大写"壹佰贰拾"和小写"120"对不上是老牌废标点，机器列清单逐项对，比人眼在小号字里捞强得多。

我们后来把勾稽拆成两次跑：周三报价定稿当天先跑一遍，周五终检再全量跑一遍。周五查出来的问题，八成周三就能拦住——终检是兜底，不是唯一的网。

## 坑三：终检靠感觉，没有总揽清单

以前所谓终检就是"再通读一遍"，而通读是最不可靠的检查方式，尤其是夜里。现在的固定动作是一条总揽提示词：

```
帮我做发布前终检：错别字、标点、数字前后一致性、表格与正文是否一致；全部用批注输出；最后给我一份问题分级摘要（严重/一般/建议）
```

跑完先看那份分级摘要："严重"级的连夜处理；"一般"和"建议"级的评估要不要动——封版前的文档，每改一处都是引入新风险，分级摘要的意义就是让你只动该动的。三百页的标书，document_meta 先看段数，document_chunks 分块过，不会因为文档大卡住；校对默认 dryRun，问题全部以批注输出，封版稿不被工具改动一个字。

还有个流程细节：终检永远在副本上跑，正本封版后只读不写。理论上批注模式动不了正文，但流程上仍然隔离副本——不是不信任工具，是不信任凌晨一点的人。批注在副本上处理完、人工确认后，改动再落回正本，每一步有据可查，出分歧时回溯成本最低。

## 内网机器上的现实约束

还有个背景值得单说：开标前夜用的那台机器是内网机，物理断外网，标书涉密不出域是硬规定，谁也别想往上装需要联网的 SaaS。察元这套东西能在这种环境跑起来，靠的是两点：一是它走本机 MCP 服务，地址 127.0.0.1:62588，只监听本机回环，文档和操作都不出这台机器；二是模型可以配 Ollama 这类本地端点，校对、勾稽、批注全程离线完成。这也是当初选它的现实原因——功能再多的 AI 工具，"文档要出域"这一条就过不了我们安全岗的关。

## 把流程钉死

现在我们组的交标前夜流程是：封版稿复制一份副本，副本上跑终检三连（表格错字、数字勾稽加口径词、总揽分级），批注清零，人工复核确认，然后才打印封标。终检是兜底，不是免责——它查出来的任何"严重"级问题，本质上都是前几天的流程债。

开标前夜睡得好不好，取决于周三之前把多少活干完了。数字一致再睡觉，这句现在贴在我们组打印机旁边。
