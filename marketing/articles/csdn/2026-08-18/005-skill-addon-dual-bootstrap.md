# 装技能等于装加载项：察元AI文档助手双向自启设计拆解

看到「察元AI文档助手」的安装脚本时，我第一反应是又见缝合怪：一个脚本又要装 WPS 加载项，又要装 MCP 服务，还要往 Claude Code、Cursor 里投技能文件，这不是把三件事搅在一起吗？用了一段时间再回头看，才发现这个"双向自启"的设计其实是整套产品最聪明的一笔。这篇就拆一拆它到底解决了什么问题。

## 先看三个角色的分工

察元的架构里有三个角色：WPS 加载项负责在文档里干活（二十九个内置助手、批注、批量替换、表格处理）；本机 MCP 服务（127.0.0.1:62588）对外暴露 46 个文档工具，是外部 AI 智能体的入口；技能文件则是投放给 Claude Code、Cursor、Codex 的"说明书"，告诉这些 Agent 有这么一组 WPS 工具可以用、怎么用。

传统分发方式会把这三样拆成三份文档三个流程：想用加载项的去 WPS 市场，想接 MCP 的手动改配置，想给 Agent 加技能的去技能目录拷文件。结果是大多数用户装了一角就停了，永远不知道另外两角存在——工具的价值被安装成本吃掉一大半。

## 一个脚本，四步闭环

察元的答案是让安装脚本把四步一口气跑完：第一步装加载项，写 jsaddons 目录加 publish.xml，WPS 打开即加载；第二步装 chayuan-mcp 单文件二进制并按平台注册开机自启（Windows 注册表 HKCU\Run、macOS LaunchAgent、Linux systemd --user）；第三步四级体检，从加载项文件到 healthz、握手、桥接工具逐层验通；第四步把技能文件投进各家的技能目录。

所谓"双向自启"就是这里的产物：你本来只想装个 WPS 加载项，结果 Claude Code 里也多了能用 WPS 的技能；你本来只想给 Claude Code 投技能，WPS 里的加载项也就位了。入口不重要，落点都是同一套能力。一行 PowerShell 就是全部：

```powershell
& {[Net.ServicePointManager]::SecurityProtocol=[Net.SecurityProtocolType]::Tls12;$w=New-Object Net.WebClient;$w.Encoding=[Text.Encoding]::UTF8;$s=$w.DownloadString('https://gitee.com/cloudshd/chayuan-wps-releases/raw/master/scripts/install-wps-skill-chayuan.ps1');if($s.Length -and $s[0]-eq[char]0xFEFF){$s=$s.Substring(1)};& ([scriptblock]::Create($s)) -Fetch}
```

## 为什么技能和工具要捆绑

现在 Claude Code 的技能生态很热，大家都在给 Agent 塞各种技能包。但技能文件本质是提示词和流程说明，没有工具支撑就是空菜谱。察元把技能投放和服务安装绑在一起，恰好保证了菜谱和厨房同时到位：Agent 读到技能知道该调 `document_chunks` 分块读长文、该用 `document_apply_ops` 批量写回（上限 200 条操作）、写批注前必须带确认标记。技能教方法，MCP 工具给手脚，加载项是最终落在纸面的那支笔。

这个设计对升级也友好：重跑同一行命令就是覆盖升级，旧配置不动。4.1.1 修了 `-Fetch` 临时解压目录不清理的问题（此前每次安装残留约 290MB），4.1.2 修了 sidecar 黑窗，一路都是同一行命令刷上来，没有额外的迁移步骤。

举个具体的例子感受两边的对齐。你让 Agent 做多文档交叉检查，直接下这句：

```text
打开目录下这几份文档，交叉检查错别字与术语是否一致
```

技能文件教它先列文档、分块读内容、汇总问题；写回那一侧，加载项提供了从插入光标处、替换、添加批注到批注加替换等多种写回方式，还有二十九个内置助手兜底。技能教方法，工具给手脚，最后落笔的都是同一套文档能力，用户在哪头发起任务都一样。

## 想只要一半怎么办

设计者留了口子：加 `-SkillOnly` 参数就只投放技能文件，不动加载项和服务，适合服务端已经就位、只想补技能的机器。对做评测和分享的人也方便：一个参数拿到干净的技能文件，直接读里面的流程编排，比装完再翻目录省事。反过来只想要 WPS 里那二十九个内置助手、暂时不碰外部 Agent 的，装完不接 MCP 就是了，加载项自身就能用，摘要、翻译、术语统一这些活不依赖外部工具。

## 一点评价

双向自启的本质是把"安装"当产品设计，而不是当运维步骤。用户不关心三件套的关系，只关心"我现在能不能让 AI 改我的文档"，这个脚本用一次执行回答了全部问题。当然边界也说清楚：技能到位不代表结果可信，批注和替换建议仍是辅助参考，定稿在人。这种把复杂度藏进脚本、把简单留给用户的思路，值得所有做企业端工具的团队抄作业。
