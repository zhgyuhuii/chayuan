# 影子双跑：候选助手后台对比不打扰用户

上个月我们吃过一次亏。周五下午，我给校对助手的系统提示加了句"宁可多报不可漏报"，顺手就让它生效了。周一早上，一份十二页的简报被三百多条批注糊满，一多半是把正确用法标成"疑似错误"。同事们安静地删了一上午批注，没人抱怨，但我知道这个月的信任额度花完了。

事后复盘，根子不在那行提示词写得多糟，而在于改动直接上了生产，没有任何对照。互联网团队早被教育过：新版本要先灰度、要 A/B 对比。AI 助手凭什么例外？今年大家都在喊 AI Agent 办公落地元年，落地的瓶颈往往不是能力，而是这种工程细节。

## 影子双跑是什么思路

察元AI文档助手的 README 里提到了影子双跑的设计方向，和版本快照、评估、晋升、回滚放在一起，属于产品规划沉淀的能力思路，不是已上线的具体按钮。它的想法很直白：候选助手不直接顶掉现役版本，而是在后台用同样的输入跑一遍，两份结果摆在一起对比，前台用户完全无感。候选版本表现稳定，再谈晋升上位。对文档场景来说这个顺序尤其重要：批注是直接写在同事要交的稿子上的，出错没有"撤回重发"的余地，防线必须前置。

这个思路打动我的点在于"不打扰用户"四个字。对照实验的成本不该由一线同事承担，他们不该是小白鼠。

## 手工版影子双跑，今天就能做

产品设计落地之前，工具层已经够我们模拟整个流程。核心是 `proofread_run` 默认 dryRun——只返回问题列表，一个字不写回文档。这就给了对比的前提：

```
先跑一遍校对（dryRun），汇总问题列表，不要先改正文；我确认后再写成批注
```

我的土办法分四步：第一，固定一批样例文档，两周更新一次，保证测试集不过时；第二，现役提示词跑一遍 dryRun，存下问题列表；第三，候选提示词同样跑一遍，存另一份；第四，人工对比两份列表，重点看新增的误报和消失的漏报——前者伤信任，后者伤效果，两头都要盯。全程不写盘、不产批注，同事完全无感，这不就是影子双跑要的效果。

对比时我记三个数：新增误报数、消失的漏报数、批注落点准确率。前两个好理解，第三个专门盯表格场景——批注钉没钉在具体错字上，一数便知。几次对比的数据留档，晋升决定就有据可查，不再靠"感觉这版不错"拍板。

## 让外部智能体帮你跑对照

手动跑两遍嫌烦，可以把对照工作交给智能体。MCP 生态正好在爆发期，Claude Code 一条命令接上察元：

```
claude mcp add --transport http chayuan-wps-mcp http://127.0.0.1:62588/mcp
```

然后在 Claude Code 里直接说：用两套校对提示词分别 dryRun 这份文档，对比两份问题列表的差异，新增项和减少项分开列出。智能体经 MCP 调用文档工具完成读取、校对、汇总，长任务用 `proofread_job_poll` 轮询即可，不用盯着等。想给同事演示"双跑到底调了哪些工具"，用 MCP Inspector 最直观：`npx @modelcontextprotocol/inspector`，类型选 Streamable HTTP，地址填 http://127.0.0.1:62588/mcp，点 Connect 就能看到工具清单和调用过程。

## 一个务实的成本提醒

双跑比单跑多花一倍 Token，别对所有助手都上。我们的经验是只对两类做：一是全员高频使用的，比如校对、术语统一，它们出问题影响面最大；二是提示词仍在快速迭代期的，稳定前每版都要过考试。已经稳定运行超过一个月的助手，降级为每月抽查一次，把算力省下来。另外双跑用的样例文档要脱敏，尤其打算借云端渠道跑对照的时候，先过一遍敏感信息检查，别让测试流程自己踩了红线。

## 边界与心得

双跑能拦住的是"改动带来的退化"，拦不住模型本身的盲区，对比通过也不等于零误报，最终落批注前还是要人工确认。这件事的真正收益是心理层面的：有影子双跑兜底，你敢更勤快地改提示词，助手进化速度反而上去了。让候选版本在影子里的表现说话，比在周会上拍胸脯有说服力得多。
